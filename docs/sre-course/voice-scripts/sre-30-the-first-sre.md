## Scene 2 · Day 1: questions before tools

chapter: ပထမနေ့ရဲ့ မေးခွန်းတွေ

> ⟪page l30_p02⟫ ကိုမင်း ပထမဆုံး စိတ်ကူးမိတာက Padauk ရဲ့ SLO တွေနဲ့ dashboard တွေကို ကူးလာဖို့ပါ၊ SLO ဆိုတာ service ဘယ်လောက် စိတ်ချရရင် လုံလောက်ပြီလို့ သဘောတူထားတဲ့ ပစ်မှတ်ပါ။ မသီရိကတော့ အဖွဲ့ကြီးအတွက် လုပ်ထားတာတွေကို ဒီအတိုင်း မကူးဘဲ Parcel နဲ့ ကိုက်အောင် ပြင်သုံးဖို့ ပြောပါတယ်။
> ဒါကြောင့် ကိုမင်းက tool မထည့်ခင် မေးခွန်း သုံးခု အရင် မေးပါတယ်။ customer ကို ဘာက အများဆုံး ဒုက္ခပေးလဲ၊ deploy ကို ဘယ်သူ လုပ်တတ်ပြီး ဘယ်နေ့အထိ ရှိမလဲ၊ တစ်နာရီ ရပ်ရင် ဘာ ဆုံးရှုံးလဲ ဆိုတာပါ။
> ⟪page l30_p02b⟫ အဖြေတွေက ရှင်းပါတယ်။ rider တွေဆီ job ခွဲပေးတဲ့ dispatch worker က အပတ်တိုင်း hang ဖြစ်ပြီး rider တွေ အလုပ်မရဘဲ စောင့်ရပါတယ်။ deploy ကို ထွက်ခါနီး engineer ပဲ လုပ်တတ်ပါတယ်။ နေ့လယ်မှာ တစ်နာရီ ရပ်ရင် ပါဆယ် ရာနဲ့ချီ နောက်ကျပါတယ်။
> ⟪page l30_p02c⟫ lesson ၁၅ မှာ မြင်ခဲ့သလို SRE တစ်ယောက်တည်းနဲ့ အဖွဲ့ မဖြစ်ပါဘူး။ ဒါကြောင့် ကိုမင်းရဲ့ တကယ့် အလုပ်က အကုန် ကိုယ်တိုင် ပြင်တာ မဟုတ်ဘဲ reliability အလုပ်ကို engineer ၈ ယောက်ကြား ဖြန့်ပေးတာပါ။
> ပထမ အပတ်တွေမှာ worker ကို restart လုပ်တာလို လက်နဲ့ ထပ်ခါထပ်ခါ လုပ်ရတဲ့ toil များနေတာ ပုံမှန်ပါ။ ဒါပေမဲ့ ops အလုပ်ကို အချိန်ရဲ့ တစ်ဝက်အောက်မှာ ထားရမယ် ဆိုတဲ့ ကန့်သတ်ချက်ကိုတော့ system ငြိမ်လာတာနဲ့ ပြန်လိုက်နာရပါမယ်။

> ⟪close page⟫ ⟪board B1 step 1⟫ SRE လို့ ကြားလိုက်ရင် အဖွဲ့ကြီး တစ်ခုကို မြင်ယောင်ကြတာ များပါတယ်။ အဲဒီလို အဖွဲ့မှာ on-call ကို လူ အများကြီး အလှည့်ကျ ယူနိုင်ပြီး အလုပ်ကို SLO၊ error budget နဲ့ automation ကနေ စနိုင်ပါတယ်။

## Scene 4 · Ko Min's diary

chapter: ကိုမင်းရဲ့ ပထမ ရက် 30

> ⟪close board⟫ ⟪page l30_p02d⟫ ပုံမှန်ဆိုရင် ပထမဆုံး SRE က ထပ်ခါထပ်ခါ ပြန်ဖြစ်နေတဲ့ outage၊ ပြန်ပြန်လောင်တဲ့ မီးကို အရင် ငြိမ်းပါတယ်၊ ငြိမ်းသွားရင် လူတိုင်း သက်သာပြီး SRE ကို ယုံလာလို့ပါ။ Parcel မှာ အဲဒီ မီးက dispatch worker ပါ။
> ဒါပေမဲ့ worker က restart လုပ်ရင် ပြန်ကောင်းသေးတယ်၊ deploy တတ်သူ ထွက်သွားရင်တော့ worker ရဲ့ fix ကိုတောင် ထုတ်လို့ မရတော့ပါဘူး။ ဒါကြောင့် ကိုမင်းက deploy ကို ပထမ၊ worker ကို ဒုတိယ၊ user check တွေကို တတိယ ထားပါတယ်။
> ⟪close page⟫ ⟪board B2 step 1⟫ ကိုမင်းရဲ့ ပထမ ရက် ၃၀ ကို ကြည့်ရအောင်။ ရက် ၃ မှာ ထွက်ခါနီး engineer နဲ့ ထိုင်ပြီး deploy အဆင့်တိုင်းကို ချရေးပါတယ်။ ရက် ၁၀ မှာ ခလုတ် တစ်ချက်နဲ့ deploy ရော rollback ရော လုပ်လို့ရလာပါပြီ၊ rollback ဆိုတာ ပြဿနာ ရှိတဲ့ ပြောင်းလဲမှုကို ဖယ်ပြီး အရင် ကောင်းခဲ့တဲ့ version ကို ပြန်ပြောင်းတာပါ။
> ⟪board B2 step 2⟫ ကောင်းတဲ့ deploy က အဆင့် တစ်ဆင့်တည်းနဲ့ ပြီးရမယ်၊ service လည်း မရပ်ရဘူး၊ ဒါပေမဲ့ အရေးအကြီးဆုံးက rollback လုပ်လို့ရတာပါ။ rollback မရှိရင် deploy ပျက်တိုင်း ပြင်ဆင်ချက် အသစ်ကို ပျာပျာသလဲ ထပ်တင်ရပါတယ်၊ ဒါကို roll forward လို့ ခေါ်ပါတယ်။ စိတ်လောပြီး ရေးတဲ့ fix က ပြဿနာ အသစ်ကို ဖြစ်စေတတ်လို့ outage တွေ ဆက်တိုက် ဖြစ်လာတတ်ပါတယ်။
> ⟪board B2 step 3⟫ ရက် ၁၄ မှာ အဲဒီ engineer ထွက်သွားပေမဲ့ deploy တွေ ဆက်လုပ်နိုင်ပါတယ်။ dispatch worker ကတော့ လိပ်စာ ရှာပေးတဲ့ service ကို timeout မထားဘဲ ခေါ်ထားလို့ အဲဒီ service နှေးတိုင်း အဆုံးမရှိ စောင့်နေတာပါ။ timeout ထည့်ပြီး အလိုအလျောက် restart လုပ်အောင် ပြင်လိုက်တော့ ရက် ၂၁ မှာ အပတ်တိုင်း ဖြစ်နေတဲ့ outage ရပ်သွားပါတယ်။
