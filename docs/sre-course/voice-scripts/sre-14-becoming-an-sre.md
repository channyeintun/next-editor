## Scene 2 · A good SRE

chapter: SRE ကောင်း တစ်ယောက်

> ⟪page l14_p02⟫ မသီရိ ရှာနေတဲ့ SRE က code ရေးရုံ မကဘဲ top-up တစ်ခု operator ဆီ ရောက်ပုံကို အောက်ဆုံး အလွှာထိ နားလည်ပြီး design လုပ်တတ်ရပါမယ်။ debug လုပ်ရင်လည်း ကြုံရာ restart မလုပ်ဘဲ Operator A နှေးလို့လား ဆိုတဲ့ hypothesis ကို data နဲ့ စစ်ပြီး incident တွေကြားက ထပ်နေတဲ့ ပုံစံကိုလည်း မြင်ရပါမယ်။
> လက်နဲ့ ထပ်ခါထပ်ခါ လုပ်ရပြီး ရေရှည် တန်ဖိုး မပေးတဲ့ ops အလုပ်၊ toil ကိုလည်း automate လုပ်ချင်လောက်အောင် မုန်းရပါမယ်။ skill လောက် အရေးကြီးတာက ပျက်မှ ပြေးပြင်တာထက် ဘာက ပျက်နိုင်လဲ ကြိုတွေးတဲ့ စိတ်ထားပါ။
> ⟪page l14_p02b⟫ SRE တွေ code ရေးပေမဲ့ တစ်နေကုန် ရေးနေတာ မဟုတ်ပါဘူး။ ဥပမာ မသီရိက Operator B နဲ့ ချိတ်တဲ့ နေရာကို ပြောင်းဖို့ သူတို့ အဖွဲ့ကို data ပြပြီး တစ်ပတ်လုံး နားချခဲ့ရပေမဲ့ တကယ် ပြောင်းလိုက်တဲ့ code က သုံးကြောင်းပဲ ရှိပါတယ်။ ရှင်းပြတတ်တာကလည်း code လောက် အရေးကြီးတာပါ။

## Scene 3 · Two ways to clear the bar

chapter: ခန့်တဲ့ စံ

> ⟪close page⟫ ⟪board B1 step 1⟫ ကြော်ငြာ ထွက်ပြီးတော့ နောက်ဆုံး ကျန်တဲ့ နှစ်ယောက်က လုံးဝ မတူပါဘူး။ တစ်ယောက်က code ရေးတာ အရမ်း သန်တဲ့ backend developer ဖြစ်ပေမဲ့ Linux နဲ့ network ကို သိပ်မသိပါဘူး။ နောက်တစ်ယောက်က ဘဏ်မှာ systems administrator လုပ်ခဲ့တဲ့ ကိုဇော်ပါ၊ server နဲ့ network ကို နက်နက် သိပေမဲ့ code နည်းနည်းပဲ ရေးဖူးပါတယ်။
> ⟪board B1 step 2⟫ Padauk က SRE ကိုလည်း developer ခန့်တဲ့ စံအတိုင်းပဲ ခန့်ပါတယ်။ ဒါပေမဲ့ software နဲ့ systems ကျွမ်းကျင်မှုကို ပေါင်းပြီး တိုင်းလို့ နှစ်ယောက်လုံး ခန့်တဲ့ စံကို ရောက်ပါတယ်၊ ရောက်ပုံသာ ပြောင်းပြန်ပါ။ SRE ကောင်းတွေက နောက်ခံ အမျိုးမျိုးကနေ လာကြတာပါ။
> ⟪board B1 step 3⟫ interview မှာလည်း အလွတ်ကျက်ရတဲ့ မေးခွန်းတွေ မမေးဘဲ သင်္ကြန် ညမှာ top-up ဘာကြောင့် နှေးလဲ ဆိုတဲ့ တကယ့် ပြဿနာကို ပေးပြီး စဉ်းစားပုံကို အသံထွက် ပြောခိုင်းပါတယ်။ ဒါပေမဲ့ SRE ရှာရ ခက်တဲ့ကြားထဲ process က ၉ ပတ် ကြာသွားလို့ candidate ကောင်း နောက်တစ်ယောက်က တခြား ကုမ္ပဏီကို ရွေးသွားခဲ့ပါတယ်။
> ⟪board B1 step 4⟫ မသီရိ တကယ် ရှာနေတာက T-shaped ကျွမ်းကျင်မှုပါ။ T ရဲ့ အလျားလိုက် မျဉ်းက app ကနေ network အထိ အလွှာ အများကြီးကို ကျယ်ကျယ် သိတာ၊ ဒေါင်လိုက် မျဉ်းက တစ်ခု နှစ်ခုမှာ နက်နက် ကျွမ်းတာပါ။ incident မှာ ပြဿနာ ဘယ် အလွှာမှာ ပုန်းနေလဲ ကြိုမသိနိုင်လို့ အကျယ်ရော အနက်ပါ လိုတာပါ။ မသီရိကိုယ်တိုင် developer ဘက် နက်တော့ Padauk က systems ဘက် နက်တဲ့ ကိုဇော်ကို ရွေးလိုက်ပါတယ်။

## Scene 4 · The onboarding staircase

chapter: Onboarding လှေကား

> ⟪close board⟫ ⟪page l14_p02c⟫ ကိုဇော် အလုပ်ကို လက်ခံပြီးတော့ မသီရိ သတိရတာက ကိုမင်းပါ။ လစာထုတ်ရက် incident မှာ ကိုမင်းကို Operator A ရဲ့ latency ကို ၁၀ မိနစ်အတွင်း စစ်ခိုင်းခဲ့ပေမဲ့ မှန်တဲ့ dashboard ကို ရှာရင်း အချိန် အများစု ကုန်သွားခဲ့ပါတယ်။ လူသစ်ကို ကိုယ့်ဘာသာ ရုန်းကန်ပြီး သင်ခိုင်းရင် ဒီလိုပဲ ဖြစ်တတ်ပါတယ်။
> ⟪close page⟫ ⟪board B2 step 1⟫ ဒါကြောင့် မသီရိက လူသစ်ကို system တွေနဲ့ အဖွဲ့ကို နားလည်အောင် လမ်းပြတဲ့ onboarding ကို on-call ဆီ တက်တဲ့ လှေကားလို ဆွဲပါတယ်။ ပထမ အဆင့်က doc တွေ ဖတ်ရင်း on-call မကျခင် သင်ရမယ့် အရာတွေရဲ့ စာရင်း၊ on-call checklist ကို လိုက်လုပ်တာပါ၊ ခေတ်နောက်ကျနေတဲ့ doc တွေ့ရင် ကိုမင်းကိုယ်တိုင် ပြင်ပါတယ်။
> ⟪board B2 step 2⟫ နောက် အဆင့်တွေက လူသစ်ရဲ့ ပထမ project အစစ်၊ starter project နဲ့ whiteboard talk ပါ။ whiteboard talk မှာ ကိုမင်းက Wallet ledger ကို ဆွဲပြီး ငွေလွှဲ တစ်ခု ဘယ်လို မှတ်တမ်းဝင်လဲ အဖွဲ့ကို ရှင်းပြရင်း သင်ယူပါတယ်။
> ⟪board B2 step 3⟫ ပြီးရင် on-call ကို နှစ်ဆင့်နဲ့ တက်ပါတယ်။ shadowing မှာ page တွေကို မသီရိ handle လုပ်တာ ကိုမင်းက ဘေးကနေ လိုက်ကြည့်ပြီး reverse shadowing မှာတော့ ကိုမင်း ကိုယ်တိုင် handle လုပ်တာကို မသီရိက ဘေးကနေ စောင့်ကြည့်ပါတယ်။ ဒီနောက်မှ အဖွဲ့ဝင်တွေ on-call ကို အလှည့်ကျ ယူတဲ့ on-call rotation ထဲ ဝင်ပါတယ်။
> ⟪board B2 step 4⟫ လှေကား တစ်လျှောက်လုံး ရေရှည် လမ်းညွှန်တဲ့ mentor က အောက်ကနေ ထောက်ထားပါတယ်။ mentor ရဲ့ အချိန် ပေးရပေမဲ့ လူသစ်တွေ on-call ကို ပိုမြန်မြန် ရောက်ပြီး ပထမ တစ်နှစ်အတွင်း အလုပ်ထွက်တာလည်း နည်းပါတယ်။
> ⟪board B2 step 5⟫ လူ မတိုးတဲ့ အဖွဲ့ငယ်ဆိုရင် နေ့စဉ် မေးလို့ရတဲ့ buddy တစ်ယောက် တွဲပေးရုံနဲ့ လုံလောက်ပါတယ်။ Padauk ကတော့ သေးပေမဲ့ မြန်မြန် ကြီးလာနေလို့ program အစစ် လုပ်ပါတယ်။ Padauk ရဲ့ ledger ကို ဘယ် course ကမှ မသင်ပေးနိုင်လို့ အဖွဲ့ကပဲ သင်ပေးရပေမဲ့ ဘယ်သူမှ အကုန် အလွတ်ကျက်စရာ မလိုပါဘူး၊ ဘယ်မှာ ရှာရမလဲ သိရင် ရပါပြီ။
