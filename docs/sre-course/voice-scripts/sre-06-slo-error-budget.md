## Scene 2 · From number to promise

chapter: SLI၊ SLO၊ SLA

> ⟪page l06_p02⟫ engineer တွေရဲ့ dashboard မှာ မနေ့က fail ဖြစ်တဲ့ top-up ၃၀၀ လို့ ပြနေပေမဲ့ ဘယ်နှခုထဲက ၃၀၀ လဲ မသိရင် များလား နည်းလား ပြောလို့ မရပါဘူး။ ဒီလို အရေအတွက် အကြမ်းကို metric လို့ ခေါ်ပါတယ်။
> မသီရိကတော့ valid ဖြစ်တဲ့ top-up အားလုံးထဲက ကောင်းတာ ဘယ်နှ ရာခိုင်နှုန်းလဲ တွက်ပြီး၊ wallet ထဲ ငွေ မလောက်တာလို user ဘက်က အမှားကိုတော့ မရေတွက်ပါဘူး။ user ကြုံရတာကို ပြတဲ့ ဒီ ရာခိုင်နှုန်းက service level indicator၊ SLI ပါ။
> ⟪page l06_p02b⟫ finance ရဲ့ ၁၀၀ ရာခိုင်နှုန်းကိုလည်း ဒီနေ့လား၊ ဒီလလား၊ ထာဝရလား မသိရင် မီလား မမီလား ပြောလို့ မရပါဘူး။ ဒါကြောင့် ပစ်မှတ်ကို ရက် ၃၀ လို တိုင်းမယ့် ကာလ၊ window နဲ့ တွဲထားမှ service level objective၊ SLO ဖြစ်ပါတယ်။
> ⟪page l06_p02c⟫ customer နဲ့ စာချုပ်ထဲမှာ ကတိပေးထားပြီး မမီရင် လျော်ကြေး ပေးရတာကတော့ service level agreement၊ SLA ပါ၊ SLO ထက် လျော့ထားလေ့ ရှိပါတယ်။ ဒါပေမဲ့ ပထမဆုံး SLO အများစုက ငွေဝင်ငွေထွက် စာရင်း၊ ledger ကို ထိန်းတဲ့ အဖွဲ့က payment service ကို ပေးတဲ့ ကတိလို အဖွဲ့ချင်းကြား ကတိတွေပါ။ မမီရင် ငွေ မလျော်ရပေမဲ့ feature အစား ပြင်ဖို့ engineering အချိန် ပေးရပါတယ်။

## Scene 3 · First SLI and two thresholds

chapter: ပထမဆုံး SLI

> ⟪page l06_p02d⟫ မသီရိက SLO ကို ရှိပြီးသား service တစ်ခုမှာ အရင် စမ်းဖို့ Top-up ကို ရွေးပါတယ်။ လစာထုတ်ရက်တွေမှာ user တွေ အထိနာဆုံးက Top-up ဖြစ်ပြီး အဖွဲ့ကလည်း စမ်းချင်နေတယ်၊ code ကလည်း Padauk ကိုယ်ပိုင်ပါ။ refund ကို လက်နဲ့ ပြန်အမ်းရတာက ပိုကြီးတဲ့ ပြဿနာလားလို့ CTO ကိုနေလင်း မေးတော့ မစခင် စစ်ကြည့်ကြပြီး refund အများစုက fail ဖြစ်တဲ့ top-up တွေကနေ လာတာ တွေ့ရပါတယ်။
> ⟪close page⟫ ⟪board B1 step 1⟫ Top-up ရဲ့ အရေးအကြီးဆုံး user လုပ်ဆောင်ချက်က ဖုန်းဘေလ် ဖြည့်တာပါ။ ခလုတ် တစ်ချက်ပဲ နှိပ်ရပေမဲ့ နောက်ကွယ်မှာ Padauk API နဲ့ ဖုန်းကုမ္ပဏီတွေဆီ ချိတ်တဲ့ operator gateway ကို ဖြတ်ပြီးမှ ဝင်ပါတယ်။ မသီရိက ပြဿနာ မရှိရင် သွားတဲ့ ဒီ ပုံမှန် လမ်း၊ happy path ကို အဝင်ပေါက် Padauk API မှာပဲ တိုင်းပါတယ်၊ အကြမ်းဖျင်း ဖြစ်ပေမဲ့ user ဘယ်လောက် အဆင်ပြေလဲ စမြင်ရပါပြီ။
> ⟪board B1 step 2⟫ ဘယ် top-up ကို ကောင်းတယ်လို့ ရေတွက်မလဲ? မစုတို့ support အဖွဲ့ရဲ့ data အရ စက္ကန့် ၄၀ လောက် စောင့်ရတဲ့ user တွေက ငွေ ဖြတ်ပြီးပြီလား မသိလို့ ထပ်နှိပ်ကြပါတယ်။ ဒါကြောင့် ဖုန်းဘေလ် ဝင်ရုံနဲ့ မလုံလောက်ဘဲ စက္ကန့် ၁၀ အတွင်း ဝင်မှ ကောင်းတယ်လို့ ရေတွက်ပါတယ်။
> ⟪board B1 step 3⟫ ဒီမှာ ကောင်းတာနဲ့ မကောင်းတာကို ခွဲတဲ့ မျဉ်း၊ threshold နှစ်ခု ပါပါတယ်။ စက္ကန့် ၁၀ က top-up တစ်ခုချင်း ကောင်းလား ခွဲပေးပြီး၊ ၉၉.၅ ရာခိုင်နှုန်းလို ပစ်မှတ်ကတော့ ကောင်းတာ ဘယ်လောက် မကြာခဏ ဖြစ်ရမလဲ သတ်မှတ်ပါတယ်။ ဒါကြောင့် latency SLO က စက္ကန့် ၁၀ မဟုတ်ဘဲ ရာခိုင်နှုန်း တစ်ခုပါ။
> ⟪board B1 step 4⟫ ဒါပေမဲ့ system အမျိုးအစား မတူရင် SLI လည်း မတူပါဘူး။ merchant တွေဆီ ငွေလွှဲတဲ့ settlement job အတွက် အရေးကြီးတာက မြန်တာ မဟုတ်ဘဲ မနက် ၆ နာရီ မတိုင်ခင် ဖိုင် အဆင်သင့် ဖြစ်ဖို့နဲ့ စာကြောင်းတိုင်း စာရင်းနဲ့ ကိုက်ဖို့ပါ။ ledger မှာတော့ ရေးပြီးသား ငွေလွှဲ တစ်ခုမှ မပျောက်ရဘူး ဆိုတဲ့ durability SLO ကို nine အများကြီးနဲ့ သီးသန့် ထားပါတယ်။
