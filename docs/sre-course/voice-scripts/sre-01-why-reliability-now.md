## Scene 2 · Hoping vs engineering

chapter: —

> ⟪page l01_p02⟫ အဖြေကတော့ ငွေ နှစ်ခါ ဖြတ်ခံရတာပါ။ ဒီလို ဖြစ်ရတာက Padauk က ဘယ်ဘက်ခြမ်းမှာ ပြထားသလို မပျက်ဖို့ပဲ မျှော်လင့်ပြီး အလုပ်လုပ်နေလို့ပါ။ ပျက်မှ လိုက်ပြင်တယ်၊ ထုတ်ပြီးရင် ဆုတောင်းထားတယ်၊ ပြဿနာ တက်ရင် ညဘက်မှာ hero တစ်ယောက်ယောက်က ကယ်ပေးလိမ့်မယ်လို့ အားကိုးထားတယ်။
> ညာဘက်ခြမ်းကတော့ engineering နဲ့ ထိန်းတဲ့ နည်းပါ။ user ခံစားရတာကို တိုင်းတယ်၊ ဘယ်လောက်ဆို လုံလောက်လဲ ဆိုတာ ကြိုသဘောတူထားတယ်၊ လူကို ပိုပင်ပန်းအောင် မလုပ်ဘဲ system ကို ပြောင်းလိုက်တယ်။ ဒီနည်းကို Site Reliability Engineering၊ အတိုကောက် SRE လို့ ခေါ်ပါတယ်။
> SRE ဆိုတာ စက်အများကြီးပေါ်မှာ run နေတဲ့ service ကြီးတွေကို၊ သူတို့ကို အားကိုးနေတဲ့ user တွေအတွက် စိတ်ချရအောင် software ရေးပြီး ထိန်းပေးတဲ့ engineer တွေရဲ့ အလုပ်ပါ။ ဒီလို စိတ်ချရတာကို reliability လို့ ခေါ်ပါတယ်။ ဒီအလုပ်ကို DevOps engineer၊ platform engineer လို နာမည် အမျိုးမျိုးနဲ့ ခေါ်ကြပေမဲ့ လုပ်ရတာကတော့ အတူတူပါပဲ။
> ပြီးတော့ ဒီလို system တွေထဲမှာ code နဲ့ server တွေ တင်မကဘဲ အဲဒါတွေကို run တဲ့ လူတွေ၊ အဖွဲ့တွေပါ ပါနေလို့ sociotechnical system လို့ ခေါ်ပါတယ်။ ဒါကြောင့် လူတွေက tool တွေနဲ့ တန်းတူ အရေးကြီးပါတယ်။

- l01_p02 (K3, left gray / right teal; cells as left / right): မပျက်ဖို့ မျှော်လင့် / engineering နဲ့ ထိန်း | ပျက်မှ လိုက်ပြင် / user ခံစားရတာကို တိုင်း | ထုတ်ပြီး ဆုတောင်း / ဘယ်လောက်ဆို လုံလောက်လဲ သဘောတူ | ညဘက် hero တွေကို အားကိုး / system ကို ပြောင်း

## Scene 3 · Build short, run long

chapter: build နဲ့ run

> ⟪close page⟫ ⟪board B1 step 1⟫ ဒီ အပြာရောင် အကွက်လေးက rewards screen ကို build လုပ်ခဲ့တဲ့ အချိန်ပါ၊ နေ့လယ် တစ်ခင်းပဲ ကြာပါတယ်။ ⟪board B1 step 2⟫ ဒါပေမဲ့ ထုတ်လိုက်တဲ့ နေ့ကစပြီး run ရတဲ့ အလုပ်က ဒီ ခရမ်းရောင် bar ရှည်ကြီးလိုပဲ နှစ်နဲ့ချီ ကြာပါတယ်။
> အဲဒီ နှစ်တွေမှာ monitoring လုပ်ရတယ်၊ ညသန်းခေါင် ပြဿနာ တက်ရင် on-call ကျနေတဲ့သူက ထဖြေရှင်းရတယ်၊ upgrade လုပ်ရတယ်၊ data ကို ထိန်းရတယ်၊ user များလာရင် capacity တိုးရတယ်၊ မလိုတော့တဲ့ နေ့မှာလည်း ဘေးကင်းကင်း ပိတ်သိမ်းရပါတယ်။ လက်ဖက်ရည်ဆိုင် တစ်ဆိုင် ဖွင့်တာ တစ်ပတ်ပဲ ကြာပေမဲ့ နေ့တိုင်း ရောင်းရတာက နှစ်နဲ့ချီ ဖြစ်သလိုပါပဲ။
> ⟪board B1 step 3⟫ အခု AI ကြောင့် build လုပ်တာ မြန်ပြီး ဈေးပေါလာပေမဲ့ run တာကတော့ ခက်တုန်းပါပဲ။ server တွေကို cloud ကနေ ငှားသုံးလာပေမဲ့ အလုပ်က ပျောက်မသွားဘဲ၊ ဘာကို ငှားမလဲ ရွေးတာ၊ ဘယ်လို config လုပ်မလဲ ဆုံးဖြတ်တာ၊ ငှားထားတဲ့ အပိုင်းတွေ ဘယ်လို ပျက်တတ်လဲ နားလည်တာဆီကို ရွှေ့သွားတာပါ။

## Scene 4 · Padauk's loan

chapter: ဖြတ်လမ်းဆိုတာ အကြွေး

> ဒါဆို ငွေ နှစ်ခါ ဖြတ်တဲ့ ပြဿနာက ဘယ်က စလာတာလဲ။ ⟪board B2 step 1⟫ လအနည်းငယ် အရင်က Top-up အဖွဲ့က promo တစ်ခုကို အချိန်မီ ထုတ်နိုင်ဖို့ idempotency key ထည့်တာကို ချန်ထားခဲ့ပါတယ်။ ဒီ key က top-up တစ်ခုချင်းကို သီးသန့် နံပါတ် ပေးထားပြီး ပြန်ပို့ရင်လည်း အဲဒီ နံပါတ်ပဲ ပါလို့၊ ငွေကို တစ်ခါပဲ ဖြတ်ပါတယ်။
> ဒီလို ဖြတ်လမ်းလိုက်တာက ချေးငွေ ယူလိုက်တာနဲ့ တူပါတယ်။ promo က အချိန်မီ ထွက်သွားပေမဲ့ အတိုး စပေးရပါပြီ။ key မရှိတော့ တစ်ခါတလေ ငွေ နှစ်ခါ ဖြတ်မိလို့၊ မသီရိတို့ အဖွဲ့က တနင်္လာနေ့တိုင်း လက်နဲ့ တိုက်စစ်ပြီး ငွေ ပြန်အမ်းရတာ ၃ နာရီ ကြာပါတယ်။
> ⟪board B2 step 2⟫ လတွေ ကြာလာတော့ retry code ကို ထိရင် ဘာ ပျက်မလဲ မသိလို့ ဘယ်သူမှ မထိရဲတော့ပါဘူး၊ ဒါလည်း အတိုးပါပဲ။ ပြီးတော့ သင်္ကြန် အကြိုည peak အချိန်မှာ ဖုန်းကုမ္ပဏီ Operator B က နှေးသွားပါတယ်။ app က အဖြေ မရတော့ retry လုပ်ပါတယ်၊ key မပါတဲ့အတွက် Top-up service က retry တိုင်းကို top-up အသစ်လို့ ထင်ပြီး ငွေ ထပ်ဖြတ်လိုက်ပါတယ်။ ဒါက ဆပ်ရမယ့် နေ့ ရောက်လာတာပါ။
> ⟪board B2 step 3⟫ တနင်္လာနေ့ အလုပ်ကလည်း ၃ နာရီကနေ ၆ နာရီအထိ ဘယ်သူမှ သတိမထားမိဘဲ တိတ်တိတ်လေး တိုးလာခဲ့ပါတယ်။ developer တွေက ဒီလို အကြွေးကို technical debt လို့ ခေါ်ပါတယ်။ ဖြတ်လမ်းက ချေးတာ၊ လက်နဲ့ ပြင်ရတဲ့ အချိန်နဲ့ code ကို ထိရမှာ ကြောက်တာက အတိုး၊ outage က ဆပ်ရမယ့် နေ့ပါ။ ဆပ်ရမယ့် နေ့ နောက်တစ်မျိုးလည်း ရှိပါသေးတယ်၊ ကြောက်လွန်းလို့ ဘယ်သူမှ deploy မလုပ်ရဲတော့တဲ့ နေ့ပါ။

## Scene 5 · What Padauk agreed afterwards

chapter: —

> ⟪close board⟫ ⟪page l01_p03⟫ သင်္ကြန် ပြီးတော့ Padauk အဖွဲ့ ထိုင်ဆွေးနွေးကြပါတယ်။ ဘယ်အဖွဲ့မှ အကြွေး လုံးဝ မရှိဘဲ မနေနိုင်ပါဘူး၊ အဲဒီလို ကြိုးစားရင်လည်း feature တစ်ခုမှ အချိန်မီ ထုတ်နိုင်မှာ မဟုတ်ပါဘူး။ ဒါကြောင့် ဘယ်အထိ ချေးလို့ရလဲ ဆိုတာကို နောက် ပြဿနာ မတက်ခင် ကြိုသဘောတူလိုက်ကြပါတယ်။
> စည်းကမ်းက သုံးချက်ပါ။ အကြွေး အားလုံးကို စာရင်း တစ်ခုထဲ ရေးမယ်၊ အတိုးက တစ်ပတ်ကို ၅ နာရီ ကျော်ရင် နောက် sprint မှာ ဆပ်မယ်၊ နောက် peak မရောက်ခင် ဆပ်ပြီးအောင် လုပ်မယ်။ Top-up ရဲ့ ၆ နာရီက ၅ နာရီ စည်းကို ကျော်နေလို့ စာရင်း ထိပ်ဆုံးကို ရောက်သွားပါတယ်။ ဒီလို ကြိုသဘောတူထားတဲ့ risk အကန့်အသတ်ကို နောက်ပိုင်းမှာ သူ့ နာမည် အမှန်နဲ့ ပြန်တွေ့ရပါမယ်။
> SRE တွေက ဒီ စာရင်းထဲက အကြွေးတွေကို code ရေးပြီး ကိုယ်တိုင် ဆပ်ပေးသလို၊ ဖြတ်လမ်း အသစ် တစ်ခု လိုက်ရင် risk ဘယ်လောက် ရှိလဲ ဆိုတာလည်း အကြံပေးပါတယ်။ feature အသစ်တွေ ဝင်လာတိုင်း အကြွေး အသစ်တွေ ပေါ်လာမှာမို့ ဒီ စာရင်းကို တစ်ခါ ရေးပြီး ပစ်ထားလို့ မရပါဘူး၊ reliability ဆိုတာ ဘယ်တော့မှ ပြီးမသွားတဲ့ အလုပ်ပါ။
