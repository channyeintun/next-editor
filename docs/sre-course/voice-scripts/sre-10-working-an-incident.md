## Scene 4 · Several hypotheses at once

chapter: Hypothesis သုံးခု တစ်ပြိုင်နက်

> ⟪close page⟫ ⟪board B2 step 1⟫ မသီရိက ဘာကြောင့် ဖြစ်နေလဲ ဆိုတဲ့ ယူဆချက်၊ hypothesis သုံးခုကို ချရေးပါတယ်၊ မနေ့က release၊ database connection pool ပြည့်နေတာနဲ့ Operator A နှေးနေတာပါ။ တစ်ခုစီကို owner တစ်ယောက်စီ ပေးပြီး မှန်ကြောင်း မဟုတ်ဘဲ မှားကြောင်း သက်သေပြဖို့ ကြိုးစားခိုင်းပါတယ်၊ ဒါမှ ကိုယ်ထင်ထားတာကိုပဲ မြင်မိတဲ့ confirmation bias ကို ကာကွယ်နိုင်ပါတယ်။
> ⟪board B2 step 2⟫ Operator A ကိုတော့ Top-up developer ကိုမင်းကို ပေးပါတယ်၊ ကိုမင်း၊ latency ကို စစ်ပြီး ၇ နာရီမှာ ပြန်ပြောပါလို့ နာမည်နဲ့ အချိန် တပ်ပြီး ခိုင်းတာပါ။ ကိုမင်းက operator အလိုက် latency ကို ဘယ်မှာ ကြည့်ရမလဲ မသိလို့ ၁၀ မိနစ်ထဲက အများစုဟာ မှန်တဲ့ dashboard ရှာရင်း ကုန်သွားပါတယ်။ ဒါ သူ့ အပြစ် မဟုတ်ပါဘူး၊ tool တွေကို incident မတိုင်ခင် ကြိုသုံးတတ်ထားရပါမယ်။
> ⟪board B2 step 3⟫ ပြင်တဲ့ အလုပ်ကို ဦးဆောင်တဲ့ operations lead က rollback လုပ်ကြည့်တော့ ဘာမှ မပြောင်းလို့ ပထမ hypothesis ပြုတ်သွားပါတယ်။ swarm ထဲက volunteer တစ်ယောက်ကလည်း database မှာ connection တွေ လွတ်နေတာ တွေ့လို့ ဒုတိယ တစ်ခုလည်း ပြုတ်ပါတယ်။ စစ်တာ သုံးခု တစ်ပြိုင်နက် လုပ်ပေမဲ့ production ပြောင်းတာကိုတော့ operations lead ကနေ တစ်ကြိမ်မှာ တစ်ခုပဲ လုပ်ပါတယ်၊ နှစ်ခု တစ်ပြိုင်နက် ဝင်ရင် ဘယ်ဟာက ဘာ ဖြစ်စေလဲ မသိနိုင်တော့လို့ပါ။
> ⟪board B2 step 4⟫ ၇ နာရီမှာ ကိုမင်းက Operator A မှာ timeout တွေ တွေ့ကြောင်း ပြောတော့ operations lead က backup endpoint ဆီ traffic လွှဲလိုက်ပါတယ်။ ကြည့်၊ နားလည်၊ ဆုံးဖြတ်၊ လုပ်တဲ့ စက်ဝိုင်းကို hypothesis တစ်ခုချင်း ပတ်ရင် နှေးလို့ လူ သုံးယောက် ရှိတော့ သုံးခု တစ်ပြိုင်နက် စစ်တာပါ။ ရှာတာကလည်း fix ရွေးနိုင်ဖို့ပါ၊ root cause တစ်ခုတည်းကို လိုက်ရှာဖို့ မဟုတ်ပါဘူး။

## Scene 5 · Make users OK first

chapter: User ကို အရင် အဆင်ပြေအောင်

> ⟪close board⟫ ⟪page l10_p03⟫ Operator A ဘာကြောင့် နှေးလဲ မသိသေးဘဲ backup endpoint ဆီ လွှဲလိုက်သလို အကြောင်းရင်း မသိခင် user ထိခိုက်မှုကို ရပ်အောင် ဒါမှမဟုတ် လျှော့အောင် လုပ်တာက mitigation ပါ။ user ကို အရင် အဆင်ပြေအောင် လုပ်ရပါတယ်၊ တစ်စိတ်တစ်ပိုင်း သက်သာတာတောင် ကောင်းပါတယ်။
> ဒီညပြီးတော့ Padauk က ဘယ်ပြဿနာမှာမဆို သုံးလို့ရတဲ့ fix စာရင်းကို ရေးထားပါတယ်၊ rollback၊ capacity တိုးတာ၊ restart လုပ်တာ၊ traffic လွှဲတာ၊ feature ပိတ်တာနဲ့ provider ပြောင်းတာပါ။
> ⟪page l10_p03b⟫ fix တိုင်းက စမ်းသပ်ချက်လည်း ဖြစ်ပါတယ်။ ဒီညက rollback က user ကို မကယ်နိုင်ပေမဲ့ release ကို သံသယ စာရင်းက ဖယ်ပေးခဲ့ပါတယ်၊ version အဟောင်းက data အသစ်ကို ဖတ်နိုင်လို့သာ လုပ်လို့ရခဲ့တာပါ။ အဲဒါကို အချိန်ဖြုန်းတာလို့ ပြောရင် ရလဒ် ဆိုးလို့ ဆုံးဖြတ်ချက်ကိုပါ ဆိုးတယ်လို့ ထင်မိတဲ့ outcome bias ပါ၊ အဲဒီတုန်းက သိတာနဲ့ ချိန်ရင် ဆီလျော်ပါတယ်။
> ဆီလျော်တဲ့ fix က ပိုဆိုးသွားလို့ အပြစ်ပေးရင် လူတွေ ချီတုံချတုံ ဖြစ်လာမှာပါ၊ ဘာမှ မလုပ်ဘဲ စောင့်တာလည်း ကုန်ကျစရိတ် ရှိတဲ့ ရွေးချယ်မှုပါ။
> ⟪page l10_p03c⟫ ဒါဆို incident ကို ဘယ်တော့ ပိတ်မလဲ? fix ပြီးတာနဲ့ မပိတ်ဘဲ စောင့်ကြည့်ချိန် ထားပြီး တည်ငြိမ်ရဲ့လား ခဏ ကြည့်ရပါတယ်။ ကျန်တဲ့ အလုပ်ကို ပုံမှန် အလုပ်ချိန်ထဲ လုပ်လို့ရပြီလား၊ မှားတဲ့ ပြောင်းလဲမှုကို rollback လုပ်ပြီး ပြန်မဝင်အောင် တားထားပြီလား၊ ဘာကြောင့်လဲ သိပြီး ထပ်မဖြစ်တော့ဘူးလား၊ အဲဒီထဲက တစ်ခု ဟုတ်ရင် ပိတ်လို့ရပါတယ်။
