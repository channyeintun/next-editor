## Scene 2 · Two kinds of systems

chapter: Complex system

> ⟪page l12_p01d⟫ Padauk က ဒီ near miss အတွက်လည်း လူကို အပြစ်မရှာဘဲ system ကို ကြည့်တဲ့ blameless postmortem ရေးတော့ ပျက်နေတဲ့ အပိုင်း ဘာမှ မတွေ့ပါဘူး။ reviewer က ပြောင်းထားတဲ့ စာကြောင်းကို စစ်ခဲ့တယ်၊ test endpoint က သူ့အလုပ်ကို လုပ်ခဲ့တယ်၊ engineer ကလည်း doc ကို ယုံခဲ့တာပါ။
> ⟪page l12_p02⟫ နာရီ တစ်လုံးလို ရိုးရှင်းတဲ့ system ကို အပိုင်းလိုက် နားလည်လို့ရပြီး ပျက်တဲ့အခါလည်း အကြောင်းရင်း ကွင်းဆက်ကို လိုက်ပြီး ကျိုးနေတဲ့ အပိုင်းကို လဲလိုက်ရုံပါပဲ။ Padauk လို complex system မှာတော့ service တွေ၊ operator တွေနဲ့ လူတွေက တစ်ခုနဲ့ တစ်ခု အမြဲ လိုက်ညှိနေကြလို့ အပိုင်းတိုင်း ကောင်းနေရင်တောင် အားလုံး ပေါင်းလိုက်တော့ ပျက်နိုင်ပါတယ်။ ဒါကြောင့် ပြင်ရမှာက အပိုင်း တစ်ခု မဟုတ်ဘဲ သူတို့ ဆက်ဆံပုံပါ။

## Scene 3 · Swiss cheese

chapter: Swiss cheese model

> ⟪close page⟫ ⟪board B1 step 1⟫ အဲဒီညကို ပုံဆွဲကြည့်ရအောင်။ Top-up ကို ကာကွယ်တဲ့ အလွှာ လေးခု ရှိပါတယ်၊ code review၊ config check၊ traffic ၅ ရာခိုင်နှုန်းကို အရင် ပို့ကြည့်တဲ့ canary နဲ့ support ရော alert ရော ပါတဲ့ နောက်ဆုံး အလွှာပါ။ အလွှာတိုင်းက အပေါက်ပေါက်နေတဲ့ ဒိန်ခဲ အချပ်လိုပါပဲ။
> ⟪board B1 step 2⟫ အဲဒီညက config ပြောင်းလဲမှုဟာ အလွှာ သုံးခုရဲ့ အပေါက်တွေကို တစ်တန်းတည်း ဖြတ်သွားပါတယ်။ reviewer က test address ကို ခွဲမသိခဲ့ပါဘူး၊ lesson ၂ က config check ကလည်း ဝန်ဆောင်ခကိုပဲ စစ်ပါတယ်၊ canary နဲ့ alert တွေကတော့ test endpoint ရဲ့ အောင်မြင်တယ် ဆိုတဲ့ အဖြေကို ယုံခဲ့ပါတယ်။ နောက်ဆုံး အလွှာမှာ ရပ်သွားတာက မစု Facebook ကြည့်မိခဲ့တဲ့ ကံကြောင့်ပါ။
> ⟪board B1 step 3⟫ အပေါက်တွေ တစ်တန်းတည်း ကျမှ incident ဖြစ်တယ် ဆိုတဲ့ ဒီ ပုံက စိတ်ပညာရှင် James Reason ရဲ့ Swiss cheese model ပါ။ အပေါက် နှစ်မျိုး ရှိပါတယ်၊ push လုပ်တာက အဲဒီည ချက်ချင်း ပွင့်တဲ့ အပေါက်ဖြစ်ပြီး operator address ကို စစ်တဲ့ check မရှိတာကတော့ လနဲ့ချီပြီး သတိမထားမိဘဲ ပွင့်နေခဲ့တဲ့ အပေါက်ပါ။
> ⟪board B1 step 4⟫ ဒါဆို အခြေခံ အကြောင်းရင်း၊ root cause က ဘယ်အပေါက်လဲ? ဘယ်တစ်ခုကို ရွေးရွေး အဖြေ တစ်ခုတည်း လိုချင်လို့ မေးတာ ရပ်လိုက်တဲ့ နေရာ သက်သက်ပါ၊ ဘယ်ဟာ ရွေးမလဲ ဆိုတာကလည်း ကိုယ့် ခေါင်းထဲက model ပေါ် မူတည်ပါတယ်။ push လုပ်တဲ့သူကို အပြစ်တင်တာက အားအနည်းဆုံး အဖြေပါ၊ သူ့နေရာမှာ ဘယ်သူ ရှိရှိ အဲဒီ doc ကို ယုံမှာမို့ပါ။
> ⟪board B1 step 5⟫ Padauk က ကြာကြာ ပွင့်နေခဲ့တဲ့ အပေါက်ကို အရင် ပိတ်ပါတယ်။ endpoint တွေကို production စာရင်းနဲ့ တိုက်စစ်တဲ့ check ထည့်ပြီး prober ကိုလည်း operator တိုင်းမှာ ဘေလ် တကယ် ဝင်လား စစ်ခိုင်းပါတယ်။

## Scene 4 · Drift toward the edge

chapter: Drift

> ⟪close board⟫ ⟪board B2 step 1⟫ တချို့ အပေါက်တွေကတော့ လနဲ့ချီပြီး ဖြည်းဖြည်းချင်း ပွင့်လာတာပါ။ Wallet အဖွဲ့က campaign တွေ မြန်မြန် ထုတ်ချင်လို့ ခြောက်လအတွင်း ဖြတ်လမ်း လေးခု လိုက်ခဲ့ပါတယ်။ release ကို အကုန် မဖြန့်ခင် တစ်ရက် စောင့်ကြည့်တဲ့ အဆင့်ကို ကျော်လိုက်တယ်၊ နှေးလွန်းတဲ့ test တစ်ခုကိုလည်း ပိတ်ထားလိုက်ပါတယ်။
> ⟪board B2 step 2⟫ ပြီးတော့ နှေးတဲ့ query တွေကို ပြင်မယ့်အစား database connection limit ကို မြှင့်လိုက်ပြီး လူ မလောက်လို့ engineer တစ်ယောက်တည်းကို on-call ခဏခဏ ယူခိုင်းပါတယ်။ တစ်ခုချင်းက အဲဒီအချိန်မှာ အဓိပ္ပာယ် ရှိပြီး ဘာမှလည်း မပျက်လို့ ဒီ ဖြတ်လမ်းတွေက ပုံမှန် ဖြစ်သွားပါတယ်။
> ⟪board B2 step 3⟫ သင်္ကြန် အကြိုညမှာတော့ မစောင့်ဘဲ ထုတ်လိုက်တဲ့ ပြောင်းလဲမှု သေးသေးလေး တစ်ခုက peak traffic အောက်မှာ နှေးတဲ့ query နဲ့ ဆုံပြီး Wallet တစ်နာရီလောက် ရပ်သွားပါတယ်။ ဒါပေမဲ့ postmortem မှာ ဆုံးဖြတ်ချက် ဆိုးဆိုး တစ်ခုမှ ရှာမတွေ့ပါဘူး။
> ⟪board B2 step 4⟫ ဘယ်သူမှ အန္တရာယ်ကို ရွေးခဲ့တာ မဟုတ်ပါဘူး။ ပိုမြန်မြန် ထုတ်ချင်တဲ့ business ဖိအားနဲ့ ပိုလွယ်တဲ့ နည်းကို ရွေးချင်တဲ့ လူ့သဘာဝက အမြဲ တွန်းနေတာပါ။ safety ပညာရှင် Jens Rasmussen က ဒီ ဖိအား နှစ်ခုကြောင့် အဖွဲ့အစည်းတွေ အန္တရာယ် အစွန်းဆီ မသိမသာ ရွေ့သွားတတ်တာကို ရှင်းပြခဲ့ပြီး ဒါကို drift လို့ ခေါ်ပါတယ်။
> ⟪board B2 step 5⟫ postmortem က မျဉ်းကို ကျော်ပြီးမှ တုံ့ပြန်တာမို့ မကျော်ခင်ကတည်းက ပြန်တွန်းနေတဲ့ safety အလုပ် လိုပါတယ်။ ဖြတ်လမ်း ယူပြီး ဘာမှ မဖြစ်တိုင်း ဒါ ဘေးကင်းတယ်လို့ ပိုယုံလာတတ်လို့ပါ။ Padauk ကတော့ အခု သုံးလ တစ်ခါ ပုံမှန်လို့ ခေါ်နေတဲ့ ဖြတ်လမ်းတွေကို ပြန်စစ်ပါတယ်။
