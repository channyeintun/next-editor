# webnode

A Node.js-compatible runtime that runs in the browser: the engine every
Node.js lesson of this app runs on. It runs real, unmodified npm packages (the
Vite dev server, Vitest, the TypeScript compiler, Express) inside Web Workers,
on an in-memory filesystem, with an npm installer, a shell, and previews served
through a service worker.

It is an engine, like `src/core/x86`: nothing here imports from the app layer.
The app wires it in from `src/runtime/webcontainer/engine.ts`.

## Scope

The scope is frozen (2026-11-19). webnode exists to run this project's runtime
lessons and starters. Its three goals, in this order:

1. **It runs the lessons and starters.**
2. **It is fast.**
3. **It uses little memory.**

The bar for 2 and 3 is the recorded baseline: what the same lesson measured
before a change ([MEASUREMENTS.md](MEASUREMENTS.md)).

**Supported: what the lessons and starters run.** Each one runs its install
command, then its run command, and shows a preview or a program's output.
Nothing else is typed into a lesson's runtime.

- **Package manager:** `pnpm install` and `pnpm dev` (a package script), from
  the npm registry, without a lockfile.
- **Lessons** (284, in 18 dependency setups):
  - the Vite 5.4 dev server, alone or with TypeScript 6, esbuild, React 19,
    Tailwind 4 (`@tailwindcss/vite`), `dom-accessibility-api`, `tabbable`,
    `axe-core`, `ms` or `zod`;
  - the Vite 7.3 dev server with Vitest 5 started through its Node API inside
    it, alone or with happy-dom and Testing Library (DOM, React, user-event,
    jest-dom), ESLint 10, `@vitest/coverage-istanbul` or `fast-check`;
  - the Vite 7.3 dev server with `@vitejs/plugin-rsc` (React Server Components);
  - concept lessons with no dependencies, whose `pnpm dev` is an `echo`.
- **Starters** (11): Vite 8 with TanStack Start and Nitro (React), with Vue,
  Solid, Svelte, plain HTML/CSS, or Kite (`vite-plugin-kite`); Express 5 under
  `node server.js` (HTMX, Alpine AJAX); Express 5 under `tsx watch`;
  `node main.js`; `tsx main.ts`.

**Not a goal:** matching Node.js, bash or Linux beyond what those setups need.
A difference from Node that no lesson, starter or user report hits is left
alone. No conformance-only work and no whole-engine reviews.

**The rule for a change:** it needs a real lesson, starter or user report that
breaks, or a measured gain in speed or memory on a real lesson or starter
(install time, time to the first preview, peak memory). No change may make
those numbers worse. A fix that would be large (a new subsystem, more than
about a day) goes to the owner first.

**The numbers** come from `bun scripts/webnode-scenarios/measure.ts`: one
lesson per setup and every starter, in headless Chrome (`--list` prints the
setups and the lessons it measures).
What they were on 2026-11-19, to compare a later run with, is in
[MEASUREMENTS.md](MEASUREMENTS.md).

**There is no other runtime.** StackBlitz's WebContainer, which webnode
replaced and which stayed as the fallback for a while, was removed on
2026-11-19: no package, no fallback, no switch in the address. So a webnode
that does not start is a lesson that does not run. Two places where it cannot
start are known and say so to the visitor: a lesson embedded on another site
(the runtime's hosts let only the editor's own origin frame them) and a
deployment that names no runtime hosts. It is verified in Chromium browsers
only; Firefox and Safari run the same code, unverified.

## How it is built

```
editor page (api.ts)          WebNode.boot() / mount / fs / spawn / on / teardown
   │  MessagePort
   ▼
runtime frame                 a hidden iframe on the RUNTIME ORIGIN, runtime.<host>
   └─ kernel worker (kernel/) owns everything shared: the filesystem (sharedfs/),
        │                     the process table, fds, pipes, ttys, listening ports
        │  per process: MessagePort (async) + SharedArrayBuffer (blocking calls)
        └─ process workers    one Web Worker per process (process/). JavaScript
                              runs in the browser's own engine; `fs.readFileSync`,
                              `child_process.execSync` … block on Atomics.wait
                              while the kernel answers.

preview iframe                on a PREVIEW ORIGIN, <session>-<port>.<host>. Its
   └─ service worker          service worker (preview/sw.ts) turns the page's HTTP
        │  MessagePort        requests and WebSockets into connections to the port
        ▼                     a process listens on, through the gateway
      gateway (preview/)      (preview/gateway.ts) in the kernel worker.
```

- **Nothing a lesson runs is on the editor's origin.** Processes run on the
  runtime origin and previews on preview origins. Those hosts serve only the
  runtime's own scripts and pages (preview/hostResponses.ts), which only the
  editor may frame, so lesson code cannot reach the editor's cookies, storage
  or API. The editor holds one MessagePort to the kernel and nothing else.
- **One filesystem, in one shared memory.** The filesystem is a Rust module
  (`sharedfs/`) that the kernel and every process run on the same shared
  WebAssembly memory, one call at a time. A process reaches it through
  `FsBackend` (process/runtime.ts): a path operation (`stat`, `readFile`,
  `readdir` …) is a function call in the process itself; open files and
  `/dev` are a synchronous round trip to the kernel, which owns every file
  descriptor. There are no per-process copies to drift. The TypeScript
  filesystem (`kernel/vfs`) is the reference the tests compare it with, and
  what the kernel uses where a shared memory cannot be made
  (`sharedFilesystem: false` at boot forces it).
- **The runtime's hosts.** In the deployment they are subdomains of the
  editor's own domain (`runtime.nexteditor.dev`,
  `<session>-<port>.nexteditor.dev`): other origins, but the same site. Lesson
  code there cannot read the editor's cookies or storage, and cannot call its
  API as the visitor (the API checks the request's origin, and a WebSocket's).
  It can set cookies for the parent domain, so the editor's sign-in cookies
  carry the `__Host-` prefix, which a subdomain cannot set
  (infra/worker/auth/session.ts): it can neither replace a visitor's session
  nor plant a sign-in. Two things remain that only a registrable domain of
  their own would remove, as StackBlitz has with webcontainer-api.io: lesson
  code can fill the parent domain's cookie jar until the editor's requests are
  refused for their size (clearing the site's cookies undoes it), and a browser
  may run a same-site frame in the editor's process (the hosts' own pages
  send `Origin-Agent-Cluster`, and cross-origin isolation already keeps each
  origin in its own agent cluster). A page there may not frame the editor
  either: the frame would be signed in (infra/worker/framing.ts). In development every `*.localhost` name is
  its own site.
- **Cross-origin isolation is required** (SharedArrayBuffer). The editor serves
  COOP/COEP and delegates isolation to the runtime frame.
- **Each project gets its own preview origins.** A preview origin is `<session>-<port>.<host>`. A reload of the page keeps its session for the same project (the `sessionKey` boot option, the page's path by default), so the preview's service worker and storage stay. Any other boot in the page (a reset for another project or lesson) mints a new session. When a session is given up (teardown), the editor asks each of its preview origins to clear itself: the host answers `POST /__webnode__/clear` from the editor's origin with `Clear-Site-Data: "storage"`, which drops that origin's storage, caches and service worker. The request carries credentials (`credentials: "include"`): Chrome ignores Clear-Site-Data on the answer to a request made without them. Cookies are not named, because that would clear the whole site's. The editor's PostHog cookies are host-only, so the runtime's hosts cannot read them.
- **Preview cookies** live in the preview service worker's own jar, with a copy in its Cache Storage, so a worker the browser stops and restarts keeps the session. They go out on requests and on WebSocket handshakes. The server sees the preview as `http://localhost:<port>`: Host, Origin and Referer are restated on that origin, and a redirect to it (Location, Content-Location, Refresh) comes back as a path on the preview. The injected client goes only into documents (navigations and frames), never into `fetch()` or XHR bodies.
- **A preview outlives its service worker.** The worker's control port lives only in its memory, and the browser stops an idle worker (Chrome after 30 s; a page's WebSocket frames go straight to the gateway, so a preview that only takes HMR updates leaves it idle). A worker without a live port asks a window for a fresh one before it answers: a request asks its own window, a WebSocket its page, and a navigation every window the worker controls, among them the document a reload replaces, which stays until the new one arrives. So Vite's full reload after a pause loads the page once, with no connect page in between (that page flashed dark between the two documents). A window's injected client acknowledges the ask at once; a document without one (JSON, an image, the connect page) never does, so the worker waits half a second for an acknowledgement and up to 3 s for the port, then shows the connect page, as on a first load or after the editor started another runtime. A request counts as in flight on its port from the moment the worker takes it, and a request whose port was replaced while it was checked goes on the newer port, so a second window's port never closes the first under a request.
- **A preview in a browser tab of its own keeps a spare port.** The editor's preview toolbar links to the preview's address (`target="_blank"`, `rel="noopener noreferrer"`; the editor's `Cross-Origin-Opener-Policy` cuts the opener as well), so the tab has no window above it and no editor to ask when the worker has lost its port. Its injected client therefore has the gateway serve one more control port while the worker still has one (`webnode:spare` to the worker, `control` to the gateway) and keeps the other end. When the worker asks, the client pings the gateway on the spare and hands it over on the answer, then keeps another; a spare that never reached a gateway, or whose runtime is gone, is never offered, so the worker does not wait for it. The tab works with the editor's preview panel closed, for as long as the editor's tab runs the project. Checked by `scripts/webnode-scenarios/preview-tab.ts`, which stops the worker as the browser stops an idle one: before, the tab's next request got a 503 and a reload showed the connect page. A document without the client in such a tab (JSON, an image) has no spare; a reload of it goes through the editor's own preview frame when that is open, and to the connect page when it is not.
- **A port is announced once its listener has stayed.** The kernel accepts
  connections as soon as a process listens, but tells the page (`port`,
  `server-ready`) 50 ms later, and says nothing of a listener that closed
  before that. Vite tries its port three times, listening and closing at once,
  a fifth of a second before its server listens; announcing those would send
  the preview to a port nothing listens on.
- **Devices.** /dev/null, /dev/stdin, /dev/stdout, /dev/stderr, /dev/tty, /dev/fd and /dev/fd/N are the kernel's, under any spelling (`//dev/null`, `/tmp/../dev/null`, a link to one, a directory linked to /dev). In the tree each one is a symbolic link to itself, root's, and the only link root owns, so a call that does not follow the last link (lstat, readlink, `rm -r` walking) also gets the device's answer through a link to / or to /dev. /dev/fd is a directory, root's dr-xr-xr-x, by every spelling of its path, as on macOS (on Linux it is a link to /proc/self/fd, and webnode has no /proc): `/dev/fd/..` is /dev (stat, lstat, access, readdir, realpath, `ls /dev/fd/..`, also through a link to / or to /dev), and a name after any other device or after /dev/fd/N goes through what is no directory: `/dev/null/..`, `/dev/null/` and `/dev/fd/0/..` are ENOTDIR (macOS says ENOENT for the last). A path that reaches one through a link therefore fails in the filesystem with ELOOP and never creates a file there; processBackend.ts sends that call to the kernel, which walks the path itself (kernel/devicePaths.ts) to find the device it names or the place in the tree it leads to. Reading /dev/stdin reads fd 0 to its end; writing /dev/stdout writes fd 1. /dev/tty is the controlling terminal: the terminal of the page process a process descends from, whatever its own stdio is. In the shell's own commands /dev/stdin, /dev/stdout, /dev/stderr and /dev/fd/N, as a redirection target or as an operand of cat, grep, sort, tee and the line filters, are the command's own descriptors (its pipe in a pipeline, its redirections), duplicated as bash does where the system has no such files; a device operand (`cat /dev/tty`, `grep x /dev/tty`) is read as it arrives. A device cannot be removed, renamed or replaced.
- **One build's scripts never run against another's.** Every script carries its build's id (buildId.ts) and asks for the others by it. That includes the preview's service worker: the editor names its build when it hands a preview a control port, and the connect page registers `/__webnode__/sw.js?v=<that build>`. A host that serves a newer build answers a request for an older one with 409. So an editor left open across a deploy is told to reload, both by the runtime frame and by a preview's connect page, instead of driving a kernel or a gateway it does not match. The browser's own service-worker update check cannot swap a newer build's worker in either. The kernel and process scripts of a named build are cached for good.
- **ES modules are linked by our own loader** (process/loader): each module is
  rewritten (es-module-lexer + sucrase) into a function and evaluated in
  dependency order, with top-level await. Import declarations are lifted to
  the top of that function, so an imported binding is usable on every line of
  its module, as in Node. The generated code uses private names for its import
  and export bindings (build/webnodeBundle.ts renames sucrase's), so a module
  may declare its own `require` or `exports`. Code a program evaluates itself
  loads through the loader too (process/loader/evaluated.ts): `Function` and
  the async and generator function constructors are the loader's, a direct
  `eval(…)` written in loaded code passes its text through the loader first,
  and every other use of the global `eval` as a value (`(0, eval)(…)`,
  `const run = eval`, `eval.call(…)`, `eval?.(…)`, `globalThis.eval`,
  `global.eval`, `self.eval`, `window.eval`) is the loader's indirect eval,
  one function for every file, whose code imports from the file that calls
  it. So `import()` in such code resolves as in Node. Code run by `vm` goes
  through the loader too. Rewritten code calls one global function,
  `__webnode_evaluated`, which is not enumerable. Nothing is loaded through
  the browser's own `import`, except by the spellings of eval the loader
  cannot see (under "Known differences").
- **A large module's rewrite is made apart, and kept between visits.**
  Rewriting an ES module of megabytes with sucrase (Vite's main chunk) holds
  some 50 MB of heap at once, and the browser is slow to give heap back to the
  system once a worker of the runtime has used it, when it does at all: that
  one rewrite kept a lesson about 100 MB higher. So before a process rewrites
  such a file (128 KB or more, of an installed package;
  process/loader/preparedEntry.ts) it asks the kernel where the file's entry is
  (`module.prepared`). The kernel reads the file, names the entry by a SHA-256
  of the file's name and bytes, and answers with the one it has: under
  `/var/cache/webnode/prepared` already, or kept by the editor's page in
  IndexedDB from an earlier visit (preparedStorage.ts) and put there now.
  Where it has none it has one made at once, in a worker it starts for that
  alone (kernel/preparedModules.ts, process/prepareHost.ts), by the Rust
  rewriter (process/loader/rewriter): that rewrite takes a fifth of the time
  and no JavaScript heap, and its memory goes with the worker. The process
  reads the entry and rewrites nothing. A module the Rust rewriter declines
  the process rewrites as before, and the worker makes its entry with sucrase
  a minute after the last module was asked for, when the starting processes'
  heaps have shrunk. An entry outlives the project that made it, so nothing a
  project runs may make or change one: that worker runs only the runtime's
  own code on the very bytes the key names, and the store is on the editor's
  origin, which a process cannot reach (it has the runtime origin's storage at
  most). Entries belong to a version: a hash of the rewrite's own source, of
  the Rust rewriter as built and of the packages the rewrite calls
  (build/webnodeBundle.ts), so a deploy that changes none of them keeps what
  browsers hold.
- **A shell that would only start one program is not started.** `sh -c` of
  one plain command (words with nothing in them a shell reads: no quoting,
  expansion, redirection or operator) whose first word is a program does
  nothing but start that program and stand for it: the shell ends as the
  program ends, of its signal too, as bash does by exec'ing the lone command
  of `-c`. That shell is a process of its own for as long as the program
  runs: a worker that takes some 37 ms to start and holds 12 MB. A lesson's
  dev server was started through two of them: the editor runs each command
  as `sh -lc <command>`, and a package manager runs a script as
  `sh -c <script>`. Now the program is started in the shell's place, with the
  environment the shell would have started with
  (process/programs/shell/environment.ts). The package manager does it for a
  script, asking the shell's own rule which lines those are (`loneProgram`
  in process/programs/shell/interpreter.ts knows the words the shell runs
  itself); a program that cannot be started is left to the shell, which says
  why. The kernel does it for any `sh -c` or `sh -lc` whose first word is
  one of the runtime's own programs (`node`, `tsx`, `npm`, `npx`, `pnpm`,
  `pnpx`, `yarn`; kernel/exec.ts): it has no shell to ask about any other
  word. Every other line starts a shell, as before.
- **Native binaries are swapped at install time** the way WebContainer does it:
  `esbuild` → `esbuild-wasm`, `rollup` → `@rollup/wasm-node`, at the same
  version, and a platform family's `wasm32-wasi` member in place of its native
  ones (process/programs/npm/substitutions.ts). The runtime reports `linux` /
  `x64` and sets `process.versions.webcontainer`, so packages that special-case
  WebContainer take the same paths here.

## Rules for code in this directory

- TypeScript is strict with `erasableSyntaxOnly` and `verbatimModuleSyntax`: no
  `enum`, no `namespace`, no constructor parameter properties; `import type` for
  types; no unused locals or parameters. The only `lib` is DOM, so worker
  globals need a local declaration.
- Never import from outside `src/core/webnode` except npm packages. Import the
  npm polyfill packages with a trailing slash so a Node test run does not pick
  the Node builtin: `buffer/`, `string_decoder/`, `punycode/`.
- A module never touches `runtime()` (process/runtime.ts) while it is being
  evaluated, only when one of its functions runs. The bundle evaluates every
  builtin before the process has booted.
- A builtin that needs a browser global a program may replace (`performance`,
  `crypto`) captures it when the module is evaluated. The same holds for time:
  a builtin never calls the global `setTimeout`, `setInterval`, `setImmediate`
  or `queueMicrotask`, nor reads `Date.now`, when it runs, because a test's
  fake clock replaces them. It defers with `nextTick`
  (process/node/eventLoop.ts) where Node uses `process.nextTick`, delivers the
  result of off-loop work with `complete()` (process/node/fs/completion.ts) or
  a thread-pool job (process/node/internal/threadPoolJob.ts), and takes a real
  timer from process/node/timers.ts.
- A member the browser cannot provide throws an error that names it. It never
  returns a made-up value. Hashes are real hashes.
- Tests sit beside the source as `<name>.test.ts`, start with
  `// @vitest-environment node`, and run with
  `npx vp test run src/core/webnode/<path>`. Type-check with
  `npx tsc --noEmit -p src/core/webnode`.

## Builtin modules

`process/node/<name>.ts` default-exports the object `require("<name>")`
returns. Sub-paths are separate files (`fs/promises` → `fs_promises.ts`, named in
the registry). A builtin imports other builtins as ordinary TypeScript modules
(`import events from "./events"`), so there is one `EventEmitter`, one `Buffer`,
one `Stream`.

What a builtin needs from the kernel it gets from `runtime()`; its tests install
a fake with `setRuntime()` (process/testing/fakeRuntime.ts).

**The reference is Node 26.12**, the `node` the conformance cases run beside:
same exports, same argument validation errors, same error `code`s (a system
error carries its properties in Node's order: errno, code, syscall, path,
dest). `process.version` reports v22.14.0 (process/platform.ts). Where Node
22.14 and 26.12 differ, webnode does what 26.12 does; "Node 22 against Node 26"
under "Known differences" lists the places known. "As in Node" in this document means both versions.

## Running it in a real browser

`scripts/webnode-harness.ts` builds the runtime, serves it with the headers and
hosts it needs, and drives headless Chrome:

```bash
bun scripts/webnode-harness.ts run 'node -e "console.log(process.version)"'
bun scripts/webnode-harness.ts cases          # the conformance cases
bun scripts/webnode-harness.ts cases pipe-    # the cases with that in their name
bun scripts/webnode-harness.ts script <file>  # a scenario script: default export (api) => Promise
bun scripts/webnode-harness.ts serve          # then open the printed URL
```

A conformance case (`test/cases/*.cjs`, `*.mjs`) runs under real Node and inside
webnode; both must print the same output and exit with the same code. A feature
is supported when a case, or a unit test against real Node, proves it. Real
Node has no `tsx` command: `watch-tsx.cjs` prints there the transcript tsx
4.23.13 gave for its steps, and `WEBNODE_CASE_TSX=<path to tsx> node
watch-tsx.cjs` drives a real tsx instead. `npm-signals.cjs` and
`npm-kill-sigint.cjs` run the `npm` on PATH under real Node (npm 10.9 and 11.20
print the same).

A scenario script drives the runtime through the steps in `test/scenario.ts`: a
terminal it types into (`api.terminal`), a server and its preview (`api.server`,
`api.preview`), `api.check`, and `api.section` for independent parts. A step
that does not hold throws; the harness then prints `FAIL` with what the
terminal printed since the last match and exits 1. A terminal step reads only
what was printed after the echo of the line it typed and after the previous
match.

`run`, `cases` and `script` exit with a status other than 0 when what they ran
failed. The harness fails at once, with a message, when its port
(`WEBNODE_HARNESS_PORT`, 5199 unless set) is taken; `WEBNODE_HARNESS_OUT` names
the build directory of a second run at the same time.

A deployment ships the scripts minified, and serves them from a Worker. Both
are checked the same way:

```bash

WEBNODE_HARNESS_TARGET=http://localhost:8787 bun scripts/webnode-harness.ts cases
```

`WEBNODE_HARNESS_FS=kernel` runs with the TypeScript filesystem instead of the
shared one. The second command above runs the cases against the hosts a
`wrangler dev` listener serves,
started with `--var WEBNODE_PREVIEW_HOST:localhost` and
`--var PUBLIC_URL:http://localhost:8787`. "Deploying" has the same for the
deployment.

Known differences from Node:

- **Node 22 against Node 26.** A program is told it runs on Node 22.14 and gets 26.12's behaviour where the two differ. The places known:
  - a package.json that cannot be read throws ERR_INVALID_PACKAGE_CONFIG (22: MODULE_NOT_FOUND);
  - `fs.rmSync` of a tree the permissions refuse reports `EACCES, Permission denied: '<path given>'` (22: `EACCES: permission denied, unlink '<entry>'`, with a different part of the tree removed), and with `recursive` and `force` a path below a file counts as missing (22: `ENOTDIR … unlink`);
  - a paused stream's `read()` with no size returns the first buffered chunk, and an end nobody observes queues no 'readable' (22 joins the buffered chunks and emits a second 'readable');
  - `readline` also ends a line at U+2028 and U+2029 (22 does not);
  - `crypto.pbkdf2(Sync)` and `hkdf(Sync)` with a key length of 0 fail with `PBKDF2 derivation failed` and `HKDF derivation failed` (22: `Deriving bits failed`);
  - the reason text of llhttp's HPE_INVALID_CONSTANT is `Expected HTTP/, RTSP/ or ICE/` (22: `Expected HTTP/`);
  - `structuredClone` is a data property of `globalThis` (22: an accessor), and `Object.prototype.toString.call(new BroadcastChannel("x"))` is `[object BroadcastChannel]` (22: `[object EventTarget]`);
  - `node -p` prints its value at the first 'beforeExit' (22: at 'exit', after the script's 'exit' listeners);
  - `new Worker(file, { execArgv: ['--watch'] })` runs the file once (22 throws ERR_WORKER_INVALID_EXEC_ARGV);
  - `console.table` measures a cell with the character widths Node 26 has (Unicode 17);
  - a recursive `readdir` names an unreadable directory below the start as the start with the names below it appended (`./nr` for a listing of `.`, `ok/../nr`, `a//nr`; 22: `nr`);
  - `fs.Dirent` has only `name` and `parentPath` (22 also has the deprecated `path`);
  - http's `end(callback)` calls the callback with null before the 'finish' listeners, or with the error the last write ended with (ERR_SOCKET_CLOSED_BEFORE_CONNECTION for a refused request); a second `end(cb)` before the finish gets null; `writableFinished` turns true only when the message finishes (22: the callback is a 'finish' listener with no argument, a refused request never calls it, a second `end(cb)` gets ERR_STREAM_ALREADY_FINISHED, and `writableFinished` can be true right after `end()`).

- **An ES module's namespace is a plain object.** Its keys are in the order the
  module declares them, not sorted, it prints as an object rather than as
  `[Module: null prototype]`, and assigning to it does not fail.
- **`AsyncLocalStorage` across `await`** on a native promise: the browser has no
  async context, so a store set by `run()` can be lost after such an `await`.
  The store does follow timers, immediates, `process.nextTick` (and so the
  callbacks net, http and streams defer with it: 'finish', 'listening', write
  callbacks) and the callbacks of asynchronous fs calls.
- **Stopping a process is not supported.** SIGSTOP, SIGTSTP, SIGTTIN and SIGTTOU do nothing (a handler still gets the last three), so `kill -STOP` neither stops nor ends a process. SIGCHLD, SIGCONT, SIGURG and SIGWINCH are ignored by default, as in POSIX. A background reader of the terminal waits instead of getting SIGTTIN, and so does an orphan of a foreground process once its parent is gone. A request from either to change the terminal's mode does nothing, where Linux stops the process with SIGTTOU.
- **A change of the terminal's size** sends SIGWINCH to the terminal's foreground process group, after `process.stdout` and `process.stderr` have emitted 'resize'. A resize to the same size sends nothing, and background jobs get the new size but no signal.
- **Signal names and numbers**: `process.kill`, `child.kill` and the `process.on('SIG…')` events accept every name in `os.constants.signals` (SIGIOT and SIGPOLL as other names for SIGABRT and SIGIO; a listener under either name of a signal runs, under its own name) and every Linux signal number. The numbers live in one table, `signals.ts`, which the kernel, the shell (its `kill -l` and `trap -l` listings too), npm and `os` share, with the rule that a process a signal ended has the status 128 + the signal's number.
- **A process's signal handler is told whether a SIGINT is the terminal's** (`ProcessRuntime.onSignal`, `listener(signal, fromTerminal)`): a Ctrl+C reaches every process of the foreground group itself, a SIGINT sent with `kill` reaches one. The shell uses it to pass on to its programs only a SIGINT they have not already got from the terminal.
- **A node process ignores SIGPIPE**, as Node does: a write to a closed pipe fails with EPIPE on the stream. The shell declares SIGPIPE handled too, and itself does to a command of its own that wrote to a pipe nobody reads what SIGPIPE would do (see "Pipelines" below), so `yes | head -1` and `sh -c 'while :; do echo y; done' | head -1` end.
- **/dev/stdout or /dev/stdin on a file** goes through the file descriptor that is already open, at its current offset. On Linux, opening them reopens the file. Reading /dev/stdin on a file does read from the start.
- **readdir('/dev')** with file types lists fd and the devices as symbolic links, because that is what the tree holds (Node on macOS: fd a directory, null and tty character devices). Their stat is a character device (or the stat of the fd), and so is their lstat, by any path; /dev/fd's lstat and stat are a directory. So lstat of /dev/stdin, /dev/stdout and /dev/stderr is a character device, where Linux and macOS have links. /dev/urandom and /dev/zero do not exist (ENOENT).
- **/dev is root's**, as on Linux (see the permissions below), so `rm -rf /` stops at /dev, and `ls -l` names `root` as the owner of /dev and its devices.
- **Processes an exited page process leaves running** can be ended with that process's `kill()`; they get no SIGHUP.
- **TypeScript is compiled by sucrase, which erases types.** Decorators, and `namespace`/`module` blocks that hold values, cannot be compiled. Loading a file that uses them throws a SyntaxError that names the syntax, the file and the line. Namespaces that hold only types, and `declare namespace`/`declare module`/`declare global` blocks, are erased.
- **A .ts/.tsx/.jsx file's format comes from where it is.** `.cts` is CommonJS and `.mts` is an ES module. In a `"type": "module"` package it is an ES module. In a `"type": "commonjs"` package it is CommonJS, and its `import`/`export` are compiled to `require`/`exports` as tsx does, so `require`, `module` and `__dirname` work. In a package with no `"type"` field its syntax decides: `import`/`export` make it an ES module, as with Node's own type stripping.
- **ES module import cycles**: exported function declarations can be called while the cycle runs, and default and namespace imports are live. A `let`/`const`/`class` export read before its module has run gives `undefined`, not Node's ReferenceError.
- **Importing a name an ES module does not export** fails at link time with Node's SyntaxError. Imports from CommonJS modules, and imports written in TypeScript files, are not checked.
- **`import()` in code the loader cannot see.** An eval reached by a name built at run time (`globalThis["ev" + "al"]`, `globalThis["eval"]`, `Reflect.get(globalThis, "eval")`), and an eval spelled other than `eval(…)` or `(…, eval)(…)` in a file sucrase cannot parse (sloppy code with a `with` statement), uses the browser's own `import()`. It cannot load a file: it rejects with the browser's TypeError (`Failed to fetch dynamically imported module: …`, or `Failed to resolve module specifier` for a package name) only after a fetch from the runtime host has failed, which can be after the program has ended with exit code 0. Node loads the module. Replacing the global `eval` would catch these but would make every direct eval indirect.
- **Functions built from text show the loader's calls.** `String(new Function("m", "return import(m)"))` shows `__webnode_evaluated("<file>").import(m)` where Node shows `import(m)`, a function of a loaded file that calls `eval(code)` shows `eval(__webnode_evaluated("<file>").source(code))`, and a use of `eval` as a value reads as `__webnode_evaluated("<file>").eval`. `Function.toString()` prints `function () { [native code] }` (Node: `function Function() { [native code] }`). Only the body given to `new Function` is rewritten, not default parameter values; code that binds a name `eval` anywhere (a variable, a function, a parameter, a catch binding) is not rewritten. The loader's eval answers `name`, `length`, its own properties, identity (`eval === globalThis.eval`, also across files) and `String(eval)` as Node does, but `Function.prototype.toString.call(eval)` gives `function () { [native code] }` and `eval.toString` is not `Function.prototype.toString`.
- **`process.nextTick` runs in Node's order.** After each macrotask (a timer, an immediate, a kernel message, an fs completion, a port message, a WebSocket event), its ticks run, then the promise jobs, and this repeats until both are empty before the next macrotask. A tick queued from a promise job runs once the promise jobs are done (process/node/eventLoop.ts `runMacrotask`).
  - A browser does not say when the promise jobs are done, so such a tick waits for a turn: a `scheduler.postTask` task at `user-blocking` priority, which runs ahead of every task already queued, including the `node` program's exit check. It carries on in one MessageChannel message with 64 listeners; the browser runs the promise jobs after each listener, so each listener is one more round. The turn's first round is a task of its own and costs about 3 µs; each further round costs about 0.2 µs. Where the browser has no `scheduler.postTask`, the turn is a MessageChannel message without priority: tasks queued before it run first, but webnode's own macrotasks still wait for the ticks.
  - A macrotask that is an event of the runtime's own has up to 64 such rounds in its own task, after its callback, so a tick queued from its promise jobs costs about 0.2 µs and no task: immediates, fs completions, kernel messages (process/host.ts listens to them with `addMacrotaskListener`), messages on the IPC channel and on a thread's control port, and a program's MessagePort after its 16th message (eventLoop.ts `addMacrotaskListener`, `macrotaskSource`). Timers and a program port's first 16 messages take the priority task.
  - A webnode macrotask that arrives while such ticks wait runs them, then waits, in order, for the promise jobs they queue. An error thrown by a macrotask or a tick is reported ('uncaughtException') before the ticks that follow it run.
  - **Unhandled rejections.** The rejections of one macrotask are reported together (every 'unhandledRejection' listener, then their ticks, then their promise jobs), after that macrotask's ticks and promise jobs. A rejection the browser reports while a turn is still running is held until that turn is over, and dropped if the promise got a handler by then. `--unhandled-rejections=throw|strict|warn|none|warn-with-error-code` work as in Node (from NODE_OPTIONS too); another value ends `node` with `node: invalid value for --unhandled-rejections`, exit 9. A rejection handled after it was reported emits 'rejectionHandled', or with no listener the warning PromiseRejectionHandledWarning. Different from Node: the browser reports a rejection in a task of its own, behind the tasks already queued, so a macrotask queued before it (an immediate, a due timer, an fs completion, a kernel message) runs first. A rejection such a macrotask handles is never reported (Node emits 'unhandledRejection' and later 'rejectionHandled'), and with no listener the process dies one such macrotask later.
  - **A MessagePort follows Node's.** A message is one macrotask for all of its listeners (on/once, addEventListener, onmessage, in the order they were added). The port's first 'message' listener of any kind starts it and holds the process; when its last one goes the port stops, and what arrives waits for the next listener; `start()` with nobody listening drops what arrives. `close()` returns first and 'close' is emitted from the event loop (the process waits for it), to `on('close')` and `addEventListener('close')` listeners in the order they were added, each with the event (a `MessagePortCloseEvent`). The closing end's 'close' comes once the caller's task, ticks and promise jobs are done, ahead of the tasks already queued: before the other end gets what was posted to it, and before its 'close'. A message that waits behind ticks is not given to a listener those ticks removed. A port its own listener closes (in the listener, its ticks or its promise jobs) still delivers, as Node's does, the messages it had received and one its peer posts in the same task, then emits 'close'; it sends nothing more, and a closed or closing port in a transfer list, of `postMessage` or of `structuredClone`, throws Node's DataCloneError (`MessagePort in transfer list is already detached`). Its own delivery includes a close() from a tick that a promise job of its listener queued (eventLoop.ts `inMacrotaskOf`). A port closed outside its own delivery gets nothing more, as in Node. An end with no message listener emits 'close' when its peer closes; a 'close' listener neither delivers messages nor holds the process. If messages wait for a listener (on an end nobody started, or one whose last listener went), 'close' comes after a later listener has had them and their ticks, or after `start()` with nobody listening drops them. Messages a port holds for its next listener (an end with only a 'close' listener, an end whose last 'message' listener went through off or once) go with it when it is transferred, by a port's postMessage, Worker.postMessage, workerData with transferList, or structuredClone, and the receiving side gets them first, in order. Different from Node: called from a timer, the main script, a tick or a promise job (anything but an immediate), Node first delivers what was posted and runs the immediates queued, then emits the closing end's 'close' (`port2.postMessage('d'); port2.close(); setImmediate(…)` gives `p1:d imm p2 close p1 close`); webnode emits it first (`p2 close p1:d imm p1 close`); from an immediate both give `p2 close p1:d imm p1 close`. The object a transferred port leaves behind emits no 'close'; while the process waits for the closing end's 'close', the peer's comes too, where Node exits without it when nothing else holds the process; and each message is a task of its own, so an immediate queued earlier can run between two messages Node delivers in one go; a message that still waits for a port is lost when such an immediate closes that port: `port1.postMessage('a'); port2.postMessage('b'); port1.postMessage('c'); setImmediate(() => { port2.postMessage('d'); port2.close(); })` with message and close listeners on both ends prints `p2:a p1:b p2 close p1:d p1 close` in webnode ('c' never reaches port2) and `p1:b p2:a p2:c p2 close p1:d p1 close` in Node.
  - A waiting WebSocket event is not given to a removed listener, nor after the program's own `close()`. A socket its peer closed still gets the messages that came before the close, then 'close'.
  - `AbortSignal.timeout` runs on Node's timers: the timer is unref'd and 'abort' fires from a macrotask. Ticks queued in other browser callbacks webnode does not wrap (DOM events of objects other than MessagePort, BroadcastChannel and WebSocket) run after the promise jobs that callback queued.
  - net and http defer with `process.nextTick` where Node does ('listening', server 'close', getConnections, listen and connect to an IP address, a second `connect()`, write after FIN, http's finish, error, abort, free and close callbacks). A listen or connect by host name, and the answer to a connect, come from the event loop, as Node's lookup and connect callbacks do; a pending lookup holds the process. Socket and http timeouts ('timeout', the server's check of headersTimeout and requestTimeout) are macrotasks. So are the head, each chunk of the body and a failure of a response that `fetch` carries from another host, and 'continue' for `Expect: 100-continue` to such a host.
  - What Node runs on its thread pool calls back from the event loop, one macrotask per callback, in the async context of the call, and holds the process while it is pending: zlib's callback functions, `crypto.randomBytes`/`randomFill`/`randomInt`, `pbkdf2`, `scrypt` and `hkdf` (process/node/internal/threadPoolJob.ts). A zlib stream finishes each chunk the same way: its output and its write callback come in a task of their own, in the async context the stream was made in; 'finish' does not wait for the last flush, and 'end' follows that flush. readline and the stream adapters defer with `process.nextTick` where Node does.
  - An ES module entry (`-e` with `--input-type=module` too, and a worker's `eval: true` source) and a CommonJS entry after `--import` run in a promise job, as in Node, so their ticks run after their promise jobs. A main module that throws into 'uncaughtException' has its ticks run before its promise jobs. With both `-r` and `--import`, the `-r` preloads' ticks run before the `--import` modules load, as in Node.
  - **'beforeExit'** listeners' ticks and promise jobs run before the process decides to exit. It is emitted again only when a listener, or what it started, left work that holds the process (a ref'd timer, an immediate, an fs call, a socket, a child), once that work has finished. When nothing holds the process, `node` runs no further macrotask (an unref'd immediate or timer, a message on an unref'd port), as Node does not; a rejection a listener left unhandled is still reported first. Different from Node: work started through a browser promise API (fetch, WebCrypto) that also finishes within the few milliseconds before the decision does not cause another 'beforeExit'.
  - Other events Node emits from `process.nextTick` come from a tick here too: child_process 'spawn', a failed spawn's 'error', `send` callbacks, 'disconnect' and an already-aborted signal; fs watcher 'close' and 'stop'; a `dns.lookup` of an IP address. What Node delivers from I/O comes from the event loop, holding the process while it waits: `dns.lookup` by name, `lookupService`, the dns queries, `fs.watchFile` polls and `fs.watch` changes.
  - Still different: an http server request's body 'end' comes before the handler's promise jobs (Node emits it after); a client socket's 'close' comes in the same macrotask as its 'end' (Node: one later); a socket's 'finish' and the callback of `end()` come in the tick batch of its last write (Node: from the event loop, after the shutdown); in one process the server's 'connection' comes before the client's 'connect'; for a response from another host, the head and the first chunk of the body are separate macrotasks (Node: one); all the output a zlib stream makes of one chunk is pushed in one task (Node: one task per `chunkSize` piece); after a tick throws into an 'uncaughtException' listener the remaining ticks and the promise jobs run at once (Node runs them after the next macrotask); a promise job queued by an 'exit' listener never runs (Node 26 runs it at a natural exit).
- **A child that cannot start** (ENOENT) still has the stdio streams it asked for, as in Node: its output streams end with no data and close, and the child's `'close'` follows the last of them; a write to its stdin fails with EPIPE in its callback, without an `'error'` event. It has `kill`, `ref` and `unref` like every child (`kill()` answers false). stdin is destroyed before `'error'` is emitted, and its own `'close'` follows the child's. The streams are plain Readable/Writable streams, not net.Sockets, so three things differ: an output stream emits no `'finish'`; with stdout and stderr both piped, a `'close'` listener on stdout runs before the child's `'close'` (Node: after it); and after a failed write, `stdin.end()` followed by another write gives `ERR_STREAM_WRITE_AFTER_END`, in the callback and as an `'error'` event on stdin, where Node's socket, which the first failure left errored, fails the second write with EPIPE in its callback alone.
- **A paused stream is read as Node 26 reads it** (process/node/stream/paused_read.ts; the streams are readable-stream 4.8, which is Node 18's code). `read()` with no size (also `read(null)`, `read(NaN)` and any size that parses as no integer) on a byte stream without an encoding returns the first buffered chunk, so `for await` yields chunk by chunk; chunks `_read` pushes at once come back one by one; `_read` is asked for the stream's own high water mark even when a buffered chunk is larger. A stream that ends while nobody observes it (not flowing, no read waiting, no 'readable' listener) queues no 'readable' event for the end: a listener added later gets one event, and a reader that reads once per 'readable' stalls with data left, as on Node 26. The callbacks of `write()` and `end()` get `null` when there was no error, as in Node. A byte stream takes any TypedArray or DataView as a chunk (`write`, `end`, `push`, `unshift`), as a Buffer over the same memory, as Node's does (stream/view_chunks.ts); an object-mode stream keeps the view. The coded errors of the stream builtin (ERR_STREAM_*, ERR_METHOD_NOT_IMPLEMENTED, ERR_MULTIPLE_CALLBACK, ERR_INVALID_ARG_TYPE, …) have Node's shape and words: plain Error/TypeError instances with an own `code`, `constructor` the base class, toString and the stack's first line `Error [CODE]: message`, which util.inspect and the uncaught report print (stream/node_errors.ts).
- **`node -e` and `node -p`** have every builtin module as a lazy global, as Node does (`node -p "os.cpus().length"`), and in a CommonJS script the name `crypto` is node:crypto while `globalThis.crypto` stays Web Crypto; a script from stdin has none. `node -p` prints its value at the first 'beforeExit' (after the script's ticks, promise jobs and timers).
- **Globals.** `queueMicrotask`, `structuredClone` and `performance` are own properties of `globalThis` with Node's descriptors, so fake-timer libraries can replace them. The globals of a dedicated browser worker that programs probe to tell where they run (`self`, `importScripts`, `WorkerGlobalScope`, `DedicatedWorkerGlobalScope`, `WorkerNavigator`, `WorkerLocation`, `location`, `postMessage`, `onmessage`, `onmessageerror`, `close`, `name`, `Worker`, `SharedWorker`, `XMLHttpRequest`, `FileReaderSync`, `requestAnimationFrame`, `cancelAnimationFrame`) are removed: they are not there at all (`'requestAnimationFrame' in globalThis` is false), as in Node. The platform's other globals remain, where Node has none: `onerror`, `dispatchEvent`, `caches`, `indexedDB`, `origin`, `isSecureContext`, `scheduler`, `crossOriginIsolated` and the platform's interface classes, such as the `GPU*`, `IDB*` and `CSS*` ones and `FileReader`. `crypto` is an own accessor with no setter, as Node's. Deleting `structuredClone` or `crypto` leaves nothing behind (deleting `queueMicrotask` or `performance` still leaves the browser's, where Node leaves nothing). The worker's own `addEventListener` and `removeEventListener` remain on `globalThis` (Node has none). The runtime's own globals (`__webnode_evaluated`, `__webnodeNativeSetTimeout`) are not enumerable: `Object.keys(globalThis)` shows no webnode name.
- **Uncaught errors and warnings.** On an error nothing caught, the 'exit' listeners run before the error is printed, as in Node, also when a Worker's 'error' event that nobody listens for ends the process (code 1); an 'uncaughtException' listener that throws ends the process with code 7 and no 'exit' listeners (in a worker thread, see `worker_threads`). The report has no source frame: Node prints the file and line, the source line and a caret above the error; webnode starts with the error. The report (and its `Node.js v22.14.0` line) is written to fd 2 directly, as Node does, so it reaches stderr's reader after everything the program wrote there, even when the program ended, destroyed or corked `process.stderr`; what a corked stream still holds is lost at exit, as in Node. An 'error' event nobody listens for prints the error alone, without Node's `node:events:… throw er; // Unhandled 'error' event` header and its `Emitted 'error' event on … instance at:` trailer. Warnings are printed by a 'warning' listener of the process's own, the first one, so `process.removeAllListeners('warning')` silences them, as in Node. The text is Node's, with the warning's `detail` and, after the first warning, the ``(Use `node --trace-warnings ...` to show where the warning was created)`` line. A warning goes out through a console, so a stderr whose reader has gone loses the warning and the process goes on. `--trace-warnings` and `--trace-deprecation` are accepted and change nothing.
- **`vm` `timeout` and `breakOnSigint` have no effect**: nothing can interrupt synchronous code in a worker. The first use prints a warning, and code that would time out in Node runs until it ends.
- **`import()` in code run by `vm`** (runInThisContext, Script, runInContext, runInNewContext, compileFunction) follows its `importModuleDynamically` option, as in Node without --experimental-vm-modules: without it, it rejects at once with ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING; with `vm.constants.USE_MAIN_CONTEXT_DEFAULT_LOADER` it loads through the loader, from `filename` when that is an absolute path and from the working directory otherwise, with Node's ExperimentalWarning; a function rejects with ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING_FLAG and is not called (webnode has no vm modules and no --experimental-vm-modules).
- **`node --watch`** is Node's watch mode as Linux runs it (process/programs/watch.ts). The supervisor runs the program in a child `node` and watches each file the child loads through that file's folder. On a change it ends the child with SIGTERM (or `--watch-kill-signal`) 200 ms after the last change of a burst, waits for it to exit (so a server's port is free) and starts it again. It prints Node's messages and clears the terminal as Node does. `--watch-path` and `--watch-preserve-output` work. `--watch --run <script>` runs the package.json script once, as Node does; `node --run <script>` runs it as Node does: `node` exits 1 for any exit code of the script but 0, and 0 when a signal ended it, and passes no signal on to the script. Differences:
  - Files a `worker_threads` Worker loads are watched: each thread posts `{"watch:require": [file]}` or `{"watch:import": [url]}` on its parentPort and the main thread passes them on, as Node does (the program's own worker 'message' listeners see them too). A thread reports each file once, where Node repeats a report for every resolve; builtins an ES module imports are not reported; a CommonJS file required from one that ESM imported is reported, where Node 26 drops it.
  - When a `require()` fails, the files watched for its creation carry the extensions webnode's own resolution tries (`.mjs`, `.cjs`, `.ts` … besides `.js`, `.json`, `.node`). They are reported only when the whole require fails, not for each nearer `node_modules` folder Node passed on its way.
  - A program that calls `process.disconnect()` and loads a file afterwards keeps running; Node's would fail with ERR_IPC_CHANNEL_CLOSED.
- **`tsx watch`** is tsx 4's watch command (process/programs/watch.ts; watchOptions.ts reads tsx's command line). It prints tsx's messages and clears the screen on a terminal. It watches the script and each file the program loads, except dot files and anything under `node_modules`, `bower_components` or `vendor`. `--include`, `--exclude`/`--ignore` and `--clear-screen=false` work. It reruns 100 ms after the last change, force-kills a program that has not stopped after 5 s, and reruns on Enter. Its event words follow chokidar: a new file is `add`, even with its first write in the same burst, a file deleted and created again within 100 ms is `change`, and a folder is `addDir` / `unlinkDir`, the `--include` folder itself too when it is removed and made again. An `--include` folder is scanned when the watch starts, as chokidar does (not into what tsx ignores, nor through links), so an entry that was there before tsx started is named by what it was when it goes: `unlinkDir` for a folder. The program has no IPC channel (`process.send` is undefined), as under tsx. With no script (`tsx watch`, or its options alone) it prints tsx's `Error: Missing required parameter "script path"` and the `tsx watch` usage and exits 1. Differences:
  - The program runs on webnode's TypeScript loader, not tsx's esbuild one, and files its program's worker threads load are not watched.
  - On a terminal tsx fits the usage's flags table to the width; webnode prints it as tsx does into a pipe. `tsx watch --help` and `tsx --help` print node's usage.
  - tsx's loader turns SIGINT and SIGTERM into `process.exit(128 + n)` inside the program. Here the signal ends a program that does not listen for it, so its `exit` listeners do not run on a restart or on Ctrl+C. The supervisor still exits 130 on Ctrl+C, as tsx does.
  - `--include`/`--exclude` globs support `*`, `**`, `?`, `[…]` and `{a,b}`, not extglobs or `{1..3}` ranges. A file an editor replaces by renaming over it, under an `--include` glob, is `add` where tsx says `change`. A file tsx watches by path that is deleted and later created again reruns the program, reported as `add`; tsx 4.23 stops watching it until the program loads it again.
  - The time in tsx's lines uses the browser's locale.
- **File permissions are enforced as Linux enforces them for a user who is not root.** Every process runs as uid 1 and gid 1, the owner of every file but /dev and its devices, which the kernel gives to root (`VfsApi.giveToRoot`): the owner bits decide, or on root's files the others' bits. The number has one home (process/platform.ts `UID`, `GID`): `process.getuid()`, `getgid()` and `getgroups()`, `os.userInfo()` and every stat report it. Search (x) is needed on every directory a path goes through, for a node program and for the shell's commands alike: `.` and `..` count, a trailing `/` looks nothing up, and links are followed. Read (r) is needed to read a file or list a directory, write (w) to write or truncate a file, and w and x on a directory to create, remove or rename an entry in it (a directory moved to another parent needs w on itself). Execute (x) is needed to run a file. The owner may always chmod and set times; on root's files and devices chmod and explicit times are refused (EPERM; `utimes` and `lutimes` report syscall utime and lutime), while setting both times to now, as `touch` does, needs only write permission (utimensat's UTIME_NOW): `touch /dev/null` works, and `touch /dev` is EACCES. `touch -a` and `touch -m` change one time only and pass the other, read from the file, as an explicit time, which needs the owner: `touch -a /dev/null` is `Operation not permitted` (1), as on Linux, where one time left alone (UTIME_OMIT) needs the owner too. `access()` answers by the same rules; on the kernel's devices it answers from the mode their stat reports (`/dev/null` and `/dev/tty` are root's crw-rw-rw-, so X_OK is refused). fstat of a descriptor on /dev/null reports the device as stat does (mode 020666, uid 0); on such a descriptor fchmod and futimes are EPERM, and fchown to any id but -1 is EPERM. Opening a device with O_DIRECTORY is ENOTDIR; a terminal descriptor is the user's crw--w----, a pipe the user's prw-------. A refusal is EACCES. A descriptor is checked when it is opened, not afterwards. The editor's own requests (mount, `fs.*`, watch) and the kernel's setup are not checked (`PermissionedVfs.privileged`), so the editor always saves a learner's files whatever their modes. /tmp is 1777. /dev is root's 0755, as on Linux: nothing can be made, removed or renamed there (EACCES, also through a link to /dev), /dev itself cannot be removed or renamed (EACCES) by any path, through a link to / too: both filesystems keep the entry of a node root owns, before they look at its kind (`unlink('/dev')` is EACCES), and neither /dev nor a device can be hard-linked (EPERM) by any path, through a link to /dev or to / too: both filesystems refuse a hard link to a node the user does not own unless it is a plain file they may read and write that is neither set-user-ID nor set-group-ID and executable, as Linux's protected hard links do (`ln dl/null x` with dl -> /dev: `ln: failed to create hard link 'x' => 'dl/null': Operation not permitted`, status 1). A new file descriptor takes the lowest number free, 0 to 2 included, as POSIX says: after `fs.closeSync(2)` the next `openSync` is 2, and an uncaught error's report, which goes to fd 2, lands in that file.
  - The only owners are the user (uid and gid 1) and root (uid and gid 0, for /dev and its devices). On the user's files group and other bits, setuid, setgid and the sticky bit change nothing, and `chown`, `lchown` and `fchown` to any other owner or group fail with EPERM (the file's own ids and -1 succeed); on root's files any id but -1 fails with EPERM, as chown(2) answers a user who is not root. mkdir keeps only the permission bits and the sticky bit of the mode it is given (`mkdirSync(p, 0o4755)` gives 0755, `0o1777` under umask 022 gives 01755), as Linux does; a file made by open or writeFile keeps setuid and setgid (04755, 02644); chmod sets any of them. Devices are recognised by their spelling before the tree is searched, so a spelling through a directory that cannot be searched still reaches them.
  - **The file mode creation mask (umask) is per process.** A process the page starts has 022; a child starts with a copy of its parent's, and a process's worker threads share its one (a word of shared memory the kernel gives the process, `umask.ts`, which the process sets itself and the kernel reads when it opens a file for it). `process.umask()` reads it; `process.umask(mask)` sets it and returns the one before, keeps only the permission bits as Linux's umask(2) does, and in a worker thread throws ERR_WORKER_UNSUPPORTED_OPERATION. Both filesystems take the mask's bits off the mode of what a process creates: `open` and `writeFile` with O_CREAT, `mkdir` (every directory of a recursive one) and `mkdtemp` (`PermissionedVfs.withUmask`). A symbolic link is 0777, and `fs.copyFile` and `fs.cp` give the copy its source's mode whatever the mask, as libuv's fchmod does, a copy of a device too (`copyFileSync('/dev/null', 'dn')` gives 0666, also onto a file that was there). `fs.copyFile` from a pipe, a terminal or a device copies nothing, as libuv on Linux copies the size fstat reports: it creates (or empties) the destination with the source's mode (`echo hi | node -e "fs.copyFileSync('/dev/stdin','c')"` leaves `c` empty, mode 0600); /dev/stdin or /dev/fd/N standing for a file is copied whole. The shell's `cp` reads such a source to its end, as GNU cp does. The editor's own requests (mount, `fs.*`) are not a process's: they create 0644 files and 0755 directories whatever a process set.
  - **Running a file needs its x bit.** Mounted files are 0644, because a mount carries no modes, so `./script.sh` needs `chmod +x` first, as after a clone that lost the bit. `sh script.sh` and `node script.js` need only read. The kernel reads a script's `#!` line itself, so x without r starts the interpreter, which is then refused. The interpreter gets the path the script was run by (`./x.sh`, or `bin/tool` from a relative PATH entry), as Linux's binfmt_script passes it, so `$0` is `./x.sh` and a refusal reads `sh: ./x.sh: Permission denied`. A PATH search skips files it may not run and fails with EACCES if it found one.
  - A spawned child's working directory is checked (search on it and on the way to it; EACCES, as libuv's child chdir) only when the caller chose it: a `child_process` `cwd` option, or a page spawn with a cwd. A child that inherits its parent's directory (every command the shell runs, a spawn with no `cwd`) is not checked, because nothing changes into it. So after a learner's `chmod 000 .` the editor still runs commands and opens a terminal there, and the learner undoes it from that shell (`node index.js` then fails as it does on Linux, MODULE_NOT_FOUND). A spawn into a directory that does not exist still starts.
  - `process.chdir` and the shell's `cd` check what chdir(2) checks: a directory, search on it and on every directory on the way. `process.chdir` throws Node's `EACCES: permission denied, chdir '<cwd>' -> '<dir>'`, and ENOENT for an empty path. After a chdir through a symbolic link `process.cwd()` is the directory itself, and `process.env.PWD` is left alone, as in Node. In a worker thread `process.chdir` throws ERR_WORKER_UNSUPPORTED_OPERATION. The shell's `cd` alone works on the path as written, as bash's logical cd does: `cd link/..` comes back to where the link is.
  - **`fs.rmSync(path, { recursive: true })`**: a tree the permissions allow goes in one go. Otherwise it is removed as Node's rmSync does on Linux: entry by entry in the order readdir lists them, each directory's contents before its own entry, stopping at the first refusal with `EACCES, Permission denied: '<path given>'`; what came before the refusal is gone. With `force` as well, a path below something that is no directory counts as missing (ENOTDIR as well as ENOENT), as for GNU `rm -f`. `fs.rm` and `fs.promises.rm` follow Node's asynchronous rimraf: they remove everything they can and name the first refusal. They lstat the path first whatever the options, so a path in a directory that may not be searched is refused as `EACCES … lstat`, and a path below a file as `ENOTDIR … lstat`.
  - `fs.mkdir`, `fs.promises.mkdir` and `fs.mkdirSync` with `recursive` follow Node's MKDirpAsync and MKDirpSync: one directory per step, on the path as the caller spelled it. Each returns the first directory it made in that spelling (`v/q/` for `v/q/`, `w//` for `w//`). A failure names the whole path in the sync form and the failed step in the async forms (`ro/a` for `ro/a/b`). A path of plain names is asked of the filesystem as one request, with the same result; only a path with `.`, `..`, empty parts or a trailing slash, and a request that is refused, takes the steps. For a relative path that request makes nothing at or above the working directory (`FsBackend.mkdir`'s floor), so a working directory that is gone answers ENOENT and is not made again, as in Node.
  - readdir lists names by code point (the order of their UTF-8 bytes) on both filesystems; Node lists them as the system gives them.
  - `name/.` walks through `name`: when `name` is missing, mkdir, open with O_CREAT, rename, copyFile, symlink and link answer ENOENT and make nothing.
  - A rename onto a directory the source lies in is ENOTEMPTY before any permission is asked, for a file source too, as Linux's rename(2) answers (macOS answers EISDIR for a file).
  - `fs.copyFile` with a directory as the source answers what the destination refuses first (ENOENT for a missing parent, EEXIST with COPYFILE_EXCL, EACCES), then EISDIR. Unlike libuv on Linux, which has emptied the destination by then and removes it, webnode leaves the destination as it was.
  - A trailing slash after a symbolic link is not followed by the calls that make, remove or move a name, as on Linux (macOS follows it): rmdir, unlink, rm (recursive or not under force) and rename answer ENOTDIR and remove nothing; mkdir, symlink and link answer EEXIST and never make the link's target, so `mkdir l/` on a link that leads nowhere is EEXIST. `rmSync('link/')` without `recursive` is ERR_FS_EISDIR, as in Node. stat, lstat, readdir, open and the others still follow `link/`. fs.rmSync names it `ENOTDIR, Not a directory: 'link/'` (Node 26's form; Node 22 says `ENOTDIR … rmdir`).
  - `fs.rmSync(tree, { recursive: true })` stops with `EACCES, Permission denied: '<tree>'` at an empty directory of mode 0000 in the tree; Node 22 on Linux removes it.
  - `fs.opendirSync` reports no path in its error; `fs.opendir` and `fs.promises.opendir` name the directory as the caller spelled it, as in Node.
  - The module loader treats a package.json as missing only for ENOENT, ENOTDIR and EISDIR. Any other read error, including EACCES on a directory that cannot be searched, throws ERR_INVALID_PACKAGE_CONFIG `Cannot read package config <path>: permission denied.`; JSON that does not parse throws `Invalid package config <path>.`
  - Relative paths are made absolute and walked from `/`, so they also need search permission on every directory above the working directory; Linux starts at the working directory. It shows only after a directory above it loses its x bit, and a chmod by absolute path undoes it.
- **A WebSocket to a local host** (localhost, *.localhost, 127.x, ::1, the machine's hostname) reaches the server a process listens with inside the runtime, as fetch does (process/node/http/localWebSocket.ts). Only remote hosts use the browser's own WebSocket. wss: to a local host is plain ws:, as https: to a local host is plain http:. If a server never answers our close frame, the socket closes with 1006 after 5 s (Node waits).
- **Asynchronous fs calls** do their work at once and deliver the result from the event loop, one completion per task (fs/completion.ts). Timers, immediates and port messages run between completions, as in Node's poll phase. The cost is about 3 µs a call. An `fs.Dir` delivers as Node's does: a read that has to read the directory answers from the event loop, the entries that read brought with it (`bufferSize`, 32 by default) answer on the next tick, `close` answers from the event loop, and `close(callback)` on a closed Dir calls back on a tick with ERR_DIR_CLOSED.
- **Starting a process** takes about 52 ms in headless Chrome on an 8 GB M1 Mac (200 `sh -c :` in a shell loop: 10.4 s). Most of it is the browser's: starting the worker and compiling the process bundle (about 32 ms, which grows with the bundle, about 1 ms per 100 KB of it unminified), then evaluating every module of it (about 12 ms). util.inspect's package (node-inspect-extracted) is the one part evaluated only when first used, by the first inspect or format (a `console.log` too): it builds Node's primordials, about 4 ms. Until then `util.inspect.colors` and `util.inspect.styles` are accessors (Node: data properties); from the first use on each member has Node's descriptor. A shell starts without a call to the kernel for the descriptors it inherits: the kernel names them in the process's init.
- **Promise state and iterator contents in `util.inspect` / `console.log`.** A browser cannot read a promise's state or an iterator's entries synchronously. A promise prints as `Promise { <state unknown> }` and a Map/Set iterator as `[Map Iterator] { <items unknown> }`, not with a made-up `<pending>` or an empty list. WeakMap/WeakSet print `{ <items unknown> }` even with `showHidden`. `console.table` of a Map or Set iterator prints an empty table. (util/webInspect.ts)
- **Browser classes print as Node's do.** URL, URLSearchParams, Headers, FormData, Blob, File, AbortSignal, AbortController, TextEncoder, TextDecoder, Event, Request and Response print the same fields as in Node. Headers show their names in lower case, and a Response body prints as `ReadableStream {}`.
- **`AsyncLocalStorage.enterWith()` outside a callback the runtime wrapped** (at top level, or after an `await` on a native promise) lasts only until the current synchronous run ends. After that it cannot be told apart from other code, so it is dropped rather than leaked into other requests.
- **Members kept as documented no-ops** (exceptions to "throws an error that names it"): `async_hooks.createHook(...).enable()` and `v8.promiseHooks` accept hooks that never run, because their users are diagnostics tools that keep working without the events. `v8.setFlagsFromString()` is accepted with no effect: engine flags cannot be changed from page JavaScript, and Node calls changing them after start-up undefined. `performance.eventLoopUtilization()` reports zeros because the browser does not report idle time, and Vite reads it unconditionally.
- **`v8.getHeapStatistics()`** reports `performance.memory`'s figures where the browser has them. Where it does not (a worker), it throws ERR_FEATURE_UNAVAILABLE_ON_PLATFORM.
- **Assertion diffs** use Node's Myers diff and collapse equal runs as Node does. Past 1000 differing lines they fall back to a plain report (common head and tail, then the other actual lines, then the other expected lines) instead of a minimal diff.
- **`crypto`**: secret keys are supported (`createSecretKey`, `KeyObject` with `type`, `symmetricKeySize`, `export`, `equals`; `createHmac`, `createCipheriv` and `hkdf` take them), so jsonwebtoken and jose HS256 work. `keyObject.toCryptoKey()` and `KeyObject.from()` throw (a CryptoKey is asynchronous in a browser). `crypto.pbkdf2` and `crypto.scrypt` derive on the process's own thread and give way to the event loop every 10 ms through `scheduler.yield()`; in a browser without it they yield through the global `setTimeout`. `pbkdf2(Sync)` and `hkdf(Sync)` with a key length of 0 fail, as Node's OpenSSL refuses them (`PBKDF2 derivation failed`, `HKDF derivation failed`); `scrypt` derives an empty key.
- **`console.table` pads a cell by the columns it takes on a terminal**, as Node does with ICU: colour codes and combining marks none, wide characters two (process/node/stringWidth.ts). `console._stdout`, `_stderr`, `_stdoutErrorHandler`, `_stderrErrorHandler`, `_ignoreErrors` and `_times` exist as in Node, and assigning `console._stdout` redirects.
- **`child_process`.** `process.send`, `process.disconnect`, `process.connected` and `process.channel` exist only in a process started with an IPC channel, as in Node (`child.send` and `child.disconnect` likewise). A forked child's messages are emitted before its `'disconnect'` and `'exit'`: a forked child that exits by itself says so last on its channel, and the parent emits 'disconnect', 'exit' and 'close' once that envelope and the kernel's exit report have both arrived, in either order, after every message the child sent. It waits up to 1 s only for a child that exited with a code without sending the envelope (its worker failed first); for a child a signal ended (killed by itself or by its parent), the parent first delivers what is already on its end of the channel, which takes two tasks. `detached: true` starts the child in a process group of its own, and `process.kill(-pid, …)` signals a group (ESRCH, as `kill ESRCH`, for a child that is not detached). `spawnSync`, `execSync` and `execFileSync` limit the output to 1 MiB by default (ENOBUFS, signal SIGTERM) and keep the read that took the output over `maxBuffer` whole, as Node does (a single 1027-byte write under maxBuffer 1000 gives 1027 bytes, ENOBUFS, signal SIGTERM); `exec`/`execFile` cut the output at `maxBuffer`, as Node's do. The sync forms return once the child has exited and the stdout and stderr pipes they capture have ended, as in Node: a descendant that still holds one keeps the call waiting (up to its `timeout`), and what it writes is part of the result. On a timeout or maxBuffer the kernel sends `killSignal` (SIGTERM by default) to the child alone, if it still runs, lets go of the pipes at once and waits for the child to end, as Node's SyncProcessRunner::Kill does: the status is the one the child ended with (`sh -c 'trap "exit 7" TERM; while :; do :; done'` gives status 7; with `trap "echo x; exit 7" TERM` the trap's write to the dropped pipe kills it with SIGPIPE), a child that ignores the signal keeps the call waiting until it ends, and what the child started runs on. A child that had already exited keeps its own status (ETIMEDOUT with status 0, signal null). Once the pipes are let go, the next write of any writer to them fails with EPIPE (and SIGPIPE where the writer does not handle it), also the first write of one whose earlier writes went without asking. A caller that ends while it waits closes them, so what a descendant writes afterwards is EPIPE. `execSync` and `execFileSync` with no `stdio` option capture stderr and pass it on to `process.stderr` when the child has ended, as Node does, so the thrown error carries it. A child's output stream given to another child as its stdio (`stdio: [first.stdout, …]`) stops being read by the parent, as in Node; what the parent had already read stays in the stream, and the first child's `'close'` is not emitted while nobody reads it. A background job the shell runs in its own process (a subshell, a group, an and-or list, a function or builtin) outlives the shell as a forked subshell does: the shell's pid exits at once (its parent's 'exit', `spawnSync`'s status, `$?`), and the job runs on in a new process that holds the shell's descriptors. So `spawnSync('sh', ['-c', '(sleep 1; echo late) & echo early'])` gives `early\nlate\n` after a second, `exec` emits 'exit' at once and its callback and 'close' a second later, and `execSync` with a shorter timeout throws ETIMEDOUT with `early\n`, as in Node. A background program (`node … & echo early`) is a process of its own and is waited for, as in Node. Differences:
  - A child's handle has no `channel` property.
- **`worker_threads`.** A thread shares its process's pid and file descriptors: when any thread closes a descriptor, every thread's stream of it stops, and what was on its way goes back to the pipe or terminal. A Worker made with `stdout: true`, `stderr: true` or `stdin: true` keeps that stream, as in Node (process/node/threadStdio.ts): `worker.stdout` and `worker.stderr` are Readables that have everything the thread wrote before 'exit' and end after it; `worker.stdin` is a Writable (null without the option); in the thread a write's callback comes when the parent's stream asks for more. A thread's `process.stdin` is at its end unless the Worker was made with `stdin: true`, as in Node. A MessagePort inside `workerData` (with `transferList`) reaches the thread. An uncaught error in a thread reaches the parent's 'error' event as Node rebuilds it: an instance of the nearest built-in error class, with its name, message, stack and its own properties that can be cloned (`code`, `errno`, `syscall`, `path`). Before it goes, the thread's own 'exit' listeners run with code 1, as in Node: a listener's throw stops the listeners after it and changes nothing else, and `process.exit(n)` in one ends the thread with n and sends no error. A thread can start threads of its own: their messages, errors and exits reach the thread that started them, and they end with it (its `process.exit()` or `terminate()`), as in Node. A value that cannot be cloned, in a port's, a channel's or a Worker's message or in `structuredClone`, throws a DataCloneError with Node's message (`() => {} could not be cloned.`). An error an 'uncaughtException' listener of a thread throws goes to the parent's 'error' event the same way, and the thread ends with 1, as in Node (on the main thread such an error ends the process with code 7). A thread's exit and 'online' reach the parent whatever the program made of `MessagePort.prototype.postMessage`; its uncaught error goes through that method, as in Node, so a spy that does not call through takes it. Differences:
  - A thread's `write` to a stream its Worker kept never returns false (Node holds the writer past the reader's high water mark), and what a thread writes in the moment before `terminate()` may be lost.
  - A stream the Worker did not keep is the process's own: the thread writes fd 1 or 2 itself. So `worker.stdout` and `worker.stderr` then carry no data and only end with the thread (Node passes the output through them), `process.stdout.isTTY` in the thread is the terminal's, and a write to a pipe whose reader has gone fails in the thread (its console keeps EPIPE quiet), where Node's fails in the main thread and ends the process with code 1.
- **BroadcastChannel reaches the threads of its own process and no other process or tab**, as in Node: its messages travel from thread to thread over a MessagePort that links each thread to the one that started it (process/node/internal/broadcastHub.ts), not through the browser's channel, which reaches every worker of the origin and joins a new channel late; so a channel a thread has just opened gets every message posted after it. It is an EventTarget with `ref()` and `unref()`, which return the channel as in Node, and `close()`, and has no `on`/`once`; it holds the process from construction until `close()` or `unref()`, whatever listens; closing one channel leaves the others of its name open. A message's `origin` is empty, as in Node. Different from Node: each message reaches each channel in a task of its own, in the order posted; Node gives one channel all the messages it has waiting in one go.
- **Pipes hold 64 KiB, as on Linux, and a writer waits for its reader.** A pipe counts the bytes buffered in the kernel and the bytes sent to a streaming reader's process that the process has not yet handed to its reader (it acknowledges each chunk as it hands it over, `fd.ack`). The kernel sends a reading process one delivery at a time: the next goes once the process has acknowledged the last, and carries everything written meanwhile (up to 64 KiB) as one chunk, so a reader sees fewer, larger chunks than there were writes. A write of at most 4096 bytes goes in whole; larger writes go in as room appears, and writers waiting on one pipe go in strictly in turn. A write of no bytes succeeds (0) even when nobody reads the pipe, without SIGPIPE, as on Linux (macOS answers EPIPE). A child nobody reads gets 128 KiB out: its pipe plus what its parent's stream took. The parent's stream stops at exactly its 64 KiB highWaterMark (65,536 bytes, in 40 of 40 measured runs); a chunk that does not fit is split, and the part past the mark goes back to the pipe. `fs.writeSync(1)` stops at 131,072 exactly. `process.stdout.write` has by then returned for its write budget's worth more; measured in 10 runs each: 133,120 with 1 KiB writes (once 199,680), 139,264 with 4 KiB writes, 163,840 with 16 KiB writes. Node 26 holds 65,536 too when each write's size divides 64 KiB or is larger than 64 KiB, but it can go over the mark: on a loaded Mac it held 68,608 to 106,496 in 7 of 36 readings. With smaller writes that do not divide 64 KiB it goes over most times: with 1,000- and 7,000-byte writes it held 65,536 to 130,536 bytes, exactly 65,536 in only 3 of 28 readings, where webnode held exactly 65,536 in 16 of 16. A Node child that writes with `process.stdout.write` gets its whole 1 MiB out.
  - A reader that stops (pause, `readline.close`) keeps what it was handed and gets nothing more: what the kernel had already sent its process goes back to the front of the pipe (the process gives it back, `fd.unread`), still counted against the pipe, for the next reader, which may be the same one. Different from Node, whose paused stream goes on reading until its buffer is full: a child that writes with `fs.writeSync(1)` while its parent has paused its stdout from the start stops after its pipe's 64 KiB and the parent's stream holds nothing (Node 22 on Linux: the child writes 126,976 bytes and the parent's stream holds 68,608). Bytes on their way to a reader that ends or closes its fd go back to the front of the pipe. While a process waits in a blocking call (spawnSync, a blocking read of a pipe it also streams, a write waiting for room), its streams stop (they also stop waiting for a terminal's input), what was on its way to it becomes its own, and it is sent nothing more until it has been answered and has received that. So a spawnSync child reading the same stdin, or a blocking read, is never starved.
  - The shell does not stream a pipe. Each read of a built-in command is a read(2) that takes at most what the command asked for (`read` 4 KiB, `head -n` 8 KiB, the filters 64 KiB), and the kernel answers a read with up to that length across several writes, as read(2) does.
  - **Writes do not wait while there is room.** A process hands its writes to a pipe or terminal (stdout, stderr, `child.stdin`, the shell's builtins) to the kernel without waiting while what the kernel has not yet confirmed is within 64 KiB and 256 writes. Past that it waits: `process.stdout` and `process.stderr` block, while `child.stdin` and the shell wait asynchronously. The first write to an fd, and the first after its pipe lost its last reader, ask the kernel; the kernel also raises a count in the sync buffer's header (slot 3, `SYNC_BROKEN`), so a writer learns of a break at once and its next write fails with EPIPE, as in Node. An empty write asks nothing and tells the process nothing, as write(2) of no bytes: the write after it still asks. A Buffer that is a view of part of a larger buffer (a slice, what a zlib stream emits, a pooled Buffer) or of shared memory is sent to the kernel as a copy of just its bytes. The shell writes a file with a blocking write, so what a built-in wrote through an fd that stays open (`exec 3>log`, a redirected group or loop, an inherited file stdout) is in the file when the next command reads it by path; what a built-in writes to a /dev/null the shell opened is not sent to the kernel at all. `node -e` printing 20,000 `console.log` lines into `wc -l` takes about 0.28 s (0.12 s of it to start `node`).
  - **`process.stdout` and `process.stderr` on a pipe are synchronous, on purpose.** Node writes them asynchronously on Linux and macOS: a write never waits, what does not fit queues in the writer's memory, and what is still queued at `process.exit()` is lost (`process.stdout.write("x".repeat(300000)); process.exit(3)` into `wc -c` gives 65536 in Node and 300000 here; a Node child nobody reads "writes" its whole megabyte into its own queue). Here output is never cut off at exit, and a producer is held to its reader's pace.
  - Bytes a reader leaves in the pipe are dropped without SIGPIPE; only a write after the reader has gone gets SIGPIPE. `writeFile` or `copyFile` to a pipe device whose reader leaves part of the way through fails with EPIPE. `spawnSync` and `execSync` report EPIPE (status and output kept) when the child exits before taking all of `input`. A WASI `fd_write` to a broken pipe returns EPIPE. A child's 'exit' reaches the parent after the replies its exit settled, so a `child.stdin` write's EPIPE (callback, then 'error') comes before 'exit', as in Node. The message the kernel writes for a worker that crashed is not written to a stderr pipe nobody reads: the process ends with code 1, not of SIGPIPE.
  - A failed write to stdout, stderr or `child.stdin` reports Node's stream error, `write EPIPE` (errno -32, syscall `write`). Every write to stdout or stderr that fails reports its error from the event loop, after whatever the kernel sent first, so a Ctrl+C that also ended the reader runs the program's SIGINT handler first; the report holds the process, which never exits before the write's callback and the 'error' event have run. `process.stdout` and `process.stderr` are writable again after a failed write (Node's dummyDestroy), so every later write fails with its own `write EPIPE`.
  - `process.stdout.end()` and `process.stderr.end()` shut a pipe or terminal down as Node's do. On a pipe 'finish' and 'close' come at once and every later write fails with `write EPIPE` (errno -32, syscall write; uncaught, the process dies with exit code 1) and reaches nobody, and the reader sees end of file only when the process exits. On a terminal end() emits 'finish' and no 'close', the first later write fails with ERR_STREAM_WRITE_AFTER_END and the next ones with EPIPE. A file is still written after end(); destroy() changes nothing.
  - As in Node, `console`, the global one included, keeps its first failed write to itself: logging once to a pipe whose reader has gone is silent, unless the console was made with `ignoreErrors: false`. A second failed console write in a later turn of the event loop is uncaught and ends the process with code 1, as in Node. The global console binds `process.stdout`/`stderr` on its first write.
  - A write with a completion (`child.stdin.write`, the package manager's output) is still delivered after its process exits; Node drops it on `process.exit()`.
  - Still different: `readSync` or `readFileSync(0)` after `process.stdin` has started on a pipe or a terminal waits for data, where Node's stdin is non-blocking and throws EAGAIN; `copyFile` to a pipe succeeds or gives EPIPE, where Linux gives EINVAL; the stdout of a child Node spawned is a socketpair, whose reader sees end of file at the child's `process.stdout.end()`, where webnode's child pipes, like a shell's, give it at exit; a reading process that is killed in the instant between being sent a chunk and the kernel hearing that it took it has that chunk given to the pipe's next reader as well, and only effects that bypass the kernel (a file written directly in the shared filesystem) can show the chunk twice.
- **A connection holds 64 KiB between its ends, and a writer waits for its reader** (byteChannel.ts). A socket counts what it wrote and the peer has not taken; the peer takes bytes while its stream is below its high water mark (64 KiB) and reports them in steps of 32 KiB. A write is handed over in pieces of at most what the peer has room for, so `write()` returns false, write callbacks and 'drain' wait, and a reader that stops holds at most its high water mark plus 64 KiB; a write larger than 64 KiB arrives in several 'data' chunks. A waiting write is cancelled with ECANCELED when its socket is destroyed, as in Node. A real loopback connection takes more before the writer stops: 2,629,632 bytes on Linux and 552,960 on macOS, of which the reader's stream holds 65,536. The preview gateway's end takes what arrives at once, and its own writes are not held back.
  - A socket holds the process until it is destroyed or unref'd, as in Node; the http agent unrefs an idle keep-alive socket, so a client script exits as soon as its last response is read. A process that exits (or is killed) with a socket open is read by its peer as a clean end ('end', then 'close' false), as when the system closes the socket.
  - A second `connect()` while the first is in flight: by name (each lookup starts its own attempt, Node's autoSelectFamily), the first attempt is cancelled and the socket fails with Node's AggregateError, code ECANCELED, empty message, errors [`connect ECANCELED <address>:<port>`]. By address, or with autoSelectFamily off (the connect's `autoSelectFamily: false`, or `net.setDefaultAutoSelectFamily(false)` for a connect that does not say), it fails with EALREADY. Once connected a second `connect()` fails with EISCONN, by address or by name. Node answers EISCONN only by address: by name Node 26 and 22 open a new connection from the same socket (Node's documentation calls a second `connect()` before 'close' undefined behaviour). Different from Node: the cancelled attempt names 127.0.0.1 (webnode's localhost lists IPv4 first; macOS tries ::1), and a connect by name with one by address in flight (or the reverse) still fails with EALREADY, where Node usually connects. The EALREADY message carries no ` - Local (address:port)` part, because this end has no port until the kernel answers. A socket given an already-aborted signal reports 'error' AbortError and 'close' in the next tick and still connects, as Node's does.
  - A connection a server drops for maxConnections is reset when its client has already sent data: the client reads ECONNRESET and 'close' with true, as Node 26 and 22 report and as Linux and macOS send it. A client that sent nothing reads a clean end. Different from Node, which closes at accept: webnode holds the dropped connection up to 20 ms for the bytes the client writes as it learns of its connection. Bytes arriving reset it at once, so a client that sends nothing sees its end up to 20 ms later than in Node.
  - A request line that is not HTTP is reported to 'clientError' with llhttp's code, reason and bytesParsed (HPE_INVALID_METHOD, HPE_INVALID_CONSTANT, HPE_INVALID_VERSION). Still different: `GET /` (HTTP/0.9) and two spaces before the target, which Node accepts, are refused with HPE_INVALID_CONSTANT; bytes that are not a line are reported only when a line ends.
- **Terminals have no capacity**: what processes print to a terminal, and what the page types, is never held back.

Not supported:

- **Native addons** (`.node` files) and any package that downloads a binary.
- **Raw TCP, TLS, HTTP/2 and UDP.** `http`/`https` to another host go through
  the browser's `fetch`, so the remote server's CORS policy applies.
- **`module.register()` loader hooks, `vm` contexts with their own globals,
  `worker_threads.receiveMessageOnPort`, the interactive `node` REPL.**
- **Install scripts of dependencies** are not run (the project's own are).
- **Mobile browsers**, like WebContainer.
- **A preview page's own service worker** (MSW's browser worker, a PWA's `sw.js`). The preview's service worker owns the origin, so `navigator.serviceWorker.register` in a preview rejects with "previews do not support page service workers", and the host answers a script it does not serve with 404.
- **`document.cookie` and the server's cookies are separate jars.** A page script cannot read cookies the server sets, even ones that are not HttpOnly (so an XSRF-TOKEN double-submit does not work). Cookies set by `document.cookie` are not sent to the server.
- **`node:test`, `node:test/reporters`, `node:sqlite`, `node:sea`, `_stream_wrap`, `_tls_common`, `_tls_wrap`.** `module.isBuiltin()` and `builtinModules` list them, as in Node, but `require` throws ERR_UNKNOWN_BUILTIN_MODULE naming the module. (`_http_agent`, `_http_client`, `_http_common`, `_http_incoming`, `_http_outgoing` and `_http_server` load and give `http`'s own classes.)
- **Asymmetric crypto**: `sign`/`verify`, `createSign`/`createVerify`, `generateKeyPair(Sync)`, `generateKey(Sync)`, `createPublicKey`/`createPrivateKey`, public/private encrypt and decrypt, Diffie-Hellman, ECDH, X.509, primes. Each throws ERR_FEATURE_UNAVAILABLE_ON_PLATFORM naming itself.
- **TLS of its own.** `tls.getCiphers()`, `tls.rootCertificates`, `tls.createSecureContext()` and `new tls.SecureContext()` throw ERR_FEATURE_UNAVAILABLE_ON_PLATFORM: the browser has the TLS and the trust store, webnode has neither.

The shell (`sh`, `jsh`) and its built-in commands:

- Every command the shell implements has a file in /bin (kernel/exec.ts), `yes`, `egrep` and `fgrep` among them, so `child_process` can start one by name.
- Pipelines: in-process stages (builtins, functions, compound commands, commands/ programs) run at the same time, each as a subshell. `exit` ends only its stage, and a stage's EXIT trap runs when it ends. The shell itself never blocks on a pipe, since its stages share one worker: a built-in command's output that does not fit is queued, and the command waits (asynchronously; Ctrl+C or SIGTERM ends the wait) when it finishes and before it reads more input. A single built-in that writes without reading (`seq`, `cat file`) can have its whole output queued, and notices a closed pipe at its next write. Command substitution reads while the command runs.
  - **A write to a pipe nobody reads** acts on the command that made it as SIGPIPE would. A built-in program (cat, seq and the like, processes of their own in bash) ends with 141 and the shell goes on. A builtin, echo and printf included, ends the subshell or stage that ran it with 141; a shell that is a process of its own (`sh file`, `sh -c`, an npm script) dies of SIGPIPE, after its EXIT trap, so `sh -c 'while :; do echo y; done' | head -1` ends. A stage whose queued output the reader refused after the command finished exits 141 too, and a filter takes no more input once its queued output was refused, also when it reads a device or descriptor it opened itself (`cat /dev/tty | head -n 1` ends at the next typed line, as in bash). So `set -o pipefail; seq 1 1000000 | head -1` gives 141, as in bash, for every output larger than the pipe plus the reader's last read (64 KiB + 8 KiB for `head`, + 4 KiB for `read`). With `trap '' PIPE` the write only fails (`echo: write error: Broken pipe`, status 1; bash prefixes `sh: line N:`), and a PIPE trap runs after the command.
  - A built-in whose write to standard output fails for another reason than a reader gone prints `<name>: write error: <reason>` (`sh: <name>: …` for a builtin of the shell) and exits 1 (`echo hi >&3` on an fd opened for reading, a closed stdout). A write to a /dev/null the shell opened is never refused, where bash refuses one opened for reading.
  - `exec` redirections are made with the fds in effect where it runs (in a pipeline stage `exec 4<&0` is the pipe) and change only the fds they name; a shell knows the fds 3 to 9 it was started with (`exec 3>&1; sh -c "echo x >&3"`). A descriptor above 2 that is closed where a child starts (`exec 3<&-`, `3>&-`), or that a `child_process` stdio list gives as 'ignore' or leaves out, is closed in the child, as libuv leaves it: the child gets EBADF (`sh: 3: Bad file descriptor`, status 1); only 0, 1 and 2 read and write /dev/null when ignored.
- Signals: between commands the shell checks for pending signals. If the event loop has not turned for 50 ms (a loop of builtins that never waits), it yields once through a MessageChannel message so the kernel's signal message can arrive. Ctrl+C or SIGTERM therefore stops `while :; do :; done`.
  - A non-interactive shell that a Ctrl+C reaches while it only waits for its programs waits for them, as bash does: it goes on if they caught the SIGINT, and dies of SIGINT if they died of it (in a pipeline the first command decides, as in bash 3.2). A SIGINT sent to the shell alone with `kill` is not passed on, as in bash: its programs run to their end and the shell goes on.
  - While a command of its own runs (a builtin, a built-in program, a command substitution), the Ctrl+C ends it. That holds for one that waits for input from a terminal or a pipe (cat, read, head, grep, wc, sort, sed, tee, `$(cat)`), alone or in a pipeline, in a script and in jsh: its read is withdrawn in the kernel and takes nothing, so what is typed next is the shell's. A built-in program that the signal stopping the shell's commands reached ends with 128 + that signal's number (130 for Ctrl+C, 143 for SIGTERM). A Ctrl+C during a command substitution ends the shell before the command the substitution belongs to runs; a trapped one runs its trap after that command.
  - A signal's trap runs after the command the signal came during, and `$?` is afterwards what it was before the trap. `read` goes on waiting after a trap that returns, as bash 3.2 does. A trapped signal that another process sent is the shell's alone, as in bash: it is not passed on to the programs the shell waits for, a built-in program runs on to its end, and so do a subshell, a pipeline stage and a command substitution (processes of their own in bash). The trap runs once the command has ended: `trap 'echo t' TERM; sleep 1; echo $?` with a SIGTERM prints `t`, `0` after the second. While `wait` waits, the trap runs at once and `wait` returns 128+n. The terminal's Ctrl+C under an INT trap still reaches the foreground programs and stops a built-in program (130). A signal the shell sends itself (`kill -TERM $$`, `kill 0`) is delivered before the next command: its trap runs there, or the shell dies of it there. A trap on a signal that does nothing by default runs too (`trap 'echo got' WINCH; kill -s WINCH $$` prints got, and so does URG); a CHLD trap runs neither for a CHLD sent to the shell nor when a child ends, as in bash 3.2 without job control.
  - A shell that a signal ends dies of that signal after its EXIT trap, so its parent sees `signal`. With an EXIT trap this holds for bash's terminating signals: HUP, INT, ILL, TRAP, ABRT, FPE, BUS, SEGV, SYS, PIPE, ALRM, TERM, XCPU, XFSZ, VTALRM, USR1 and USR2; the shell declares them handled. SIGQUIT, SIGPROF and SIGKILL (and SIGIO, SIGPWR, SIGSTKFLT) end it without the EXIT trap, as in bash 3.2: `sh -c 'trap "echo bye" EXIT; kill -QUIT $$; echo no'` prints nothing and dies of SIGQUIT (131). A trap on the signal itself still runs, and so does the EXIT trap after it. Different from bash 3.2, which runs no EXIT trap at all when the signal comes from a `kill $$` that is the last command of `-c` (`sh -c 'trap "echo bye" EXIT; kill -TERM $$'` prints nothing there, and `bye` here). Without one, a signal the shell has no use for ends it in the kernel at once. A SIGTERM, SIGHUP or SIGQUIT with no trap is first passed on to every program the shell runs in the foreground, all of a pipeline's, and the shell then dies of it at once without waiting for them (bash dies at once too, but leaves its programs running); with a trap the shell passes nothing on, waits for the programs and then runs the trap. `exit N` in an EXIT trap is the status the shell or subshell ends with; `exit` without an operand there keeps the status it was ending with; a shell that a signal was ending still dies of that signal after the trap. After `exec <program>` there is no shell left and its EXIT trap does not run; when the program cannot start the shell ends as usual and the trap runs.
  - `sh -c '<one simple command>'` and `exec` end as the program did, signal included, as if exec'd (though the pid differs), so `sh -c 'node --watch server.js'` and `npm run dev` give 0 on Ctrl+C. While that program runs the shell stands for it: every signal sent to the shell that a process can handle (SIGUSR1 and SIGUSR2 too) is passed on to the program and the shell does nothing itself, so a program that shuts down on SIGTERM and exits 0 gives 0, and `child.kill('SIGINT')` on `sh -c '<program>'` or on `npm run x` ends the program (exit null, SIGINT). A Ctrl+C is not passed on again: the program has it from the terminal. SIGKILL sent to the shell ends only the shell. `exec` of a built-in program (sleep, cat) ends the shell of the signal that stopped it.
  - An interactive jsh abandons the command line (status 130) when Ctrl+C arrives while no foreground child runs; a foreground child that gets Ctrl+C still decides for itself. When a foreground program dies of SIGINT inside a loop (also in a subshell or a pipeline inside the loop) jsh abandons the command line, as bash does, so `while :; do node x.js; done` can be stopped; in a plain list (`a; b`) it goes on to b, as bash 3.2. A subshell, or a compound stage of a pipeline, whose program died of the Ctrl+C ends there with 130 and the command line goes on after it, as in bash 3.2. A Ctrl+C that arrives in the same chunk as the Enter of a command line cancels that line; one that reaches jsh while no command runs has its trap run and abandons nothing of the next line. An interactive shell ignores SIGTERM and SIGQUIT. A SIGHUP ends it: it passes the SIGHUP on to its foreground program and to every job still listed (to the job's process group; `disown` takes jobs off the list, `disown -h` keeps them listed and spares them the hangup), runs its EXIT trap and dies of SIGHUP.
  - Under job control (an interactive jsh) a background program starts in a process group of its own, so the terminal's Ctrl+C does not reach it. Without job control (`sh -c`, a script, a subshell) a background program stays in the shell's process group and reads /dev/null: the terminal's Ctrl+C reaches it, and a node program dies of it, as under bash (`sh -c 'node srv.js & node wait.js'`, an npm script with `&`). Background jobs the shell runs in its own process ignore it.
  - Still different from bash: `$?` after Ctrl+C on `read` at the jsh prompt is 130 (bash 3.2: 1). After Ctrl+C on `{ node catch.js; echo x; } | cat`, where the program caught the SIGINT, a non-interactive shell dies of SIGINT; bash 3.2 goes on (its first stage, a subshell, lived). `(kill -TERM $$; echo sub-after)` does not print sub-after; in bash the subshell is another process and prints it. A background shell (`sh x.sh &` in a script) is reached by the terminal's Ctrl+C, and dies of a SIGQUIT its parent shell passes on (131); in sh it inherits SIGINT and SIGQUIT ignored and goes on (its EXIT trap runs at its own end, status 0). A trapped signal that reaches an interactive jsh while it waits at its prompt has its trap run when the next line is entered; bash runs it while it waits.
- Background jobs run in the shell's own process get a pid of their own, counting up from 4194304 (2^22, above any kernel pid). That pid is known only to the shell: it sets `$!` and works with the shell's `kill` and `wait`, and no other process can signal it. `kill` ends such a job at its next command, wakes its sleeping built-in commands and forwards the signal to every program the job runs, a pipeline's included, also while a stage of the shell's own still runs; the job's status is 128+n, as a process's would be. CHLD, CONT, URG, WINCH and the stop signals leave the job running. A job's commands stop only on its own `kill`: a Ctrl+C or SIGTERM meant for the foreground leaves background jobs alone, and children a background job waits on are not foreground children.
  - A shell that ends while such jobs still run goes on as a new process for them (`processes.forkAndExit(status)`, process/runtime.ts: fork(2) with the parent's exit, the one fork a worker can do). The shell's pid is reported ended with its status to everyone who waits for it and names no process from then on; the worker goes on under a new pid, the orphan a forked child would be (out of the terminal's foreground, in the same process group), its descriptors kept open, and its children, threads, ports and connections its own. `$$` and `$PPID` keep the shell's values in those jobs. A signal sent to the new process ends them all, except SIGINT, SIGQUIT and what the shell ignored, which a job of a shell without job control ignores. Different from bash: a signal jsh does not handle (SIGKILL) still ends the jobs with the shell; one signal to the new process ends every job, where each would be a process of its own; and when an interactive jsh is told `exit` while such a job runs, the job runs to its end but what it prints to the terminal afterwards is not shown, because the page's output stream of a process ends at its exit (bash 3.2 on macOS loses it too, with EIO).
  - `kill %N` is for the whole job: in jsh it signals the process group of the job's program (for a job run in the shell's process, the group of each program it waits for), so what a program started gets the signal too. `kill <pid>` reaches that process alone, and without job control `%N` signals the program only. `kill -0` asks the kernel whether the process or group is there. `kill` reads `--` after the signal option (`kill -9 -- -<pgid>`) and refuses a number or name that is no signal. `kill -l` and `trap -l` print the whole signal table numbered, five to a line, as bash 5; `kill -l N` gives a name (also for an exit status 128+N), `kill -l NAME` a number.
  - `wait` returns 128+n when a signal reaches the shell first, and the job goes on; after the signal's trap has run `$?` is still that status. `wait` without operands returns 0 once every job has ended. `wait <pid>` also answers for a job that has left the list (reported at the prompt, listed by `jobs`, waited for before): the shell keeps the newest 1024 statuses and gives the same answer again, as bash does outside POSIX mode (/bin/sh says 127 the second time). Every job spec bash 3.2 takes names a job for `kill`, `wait`, `disown`, `jobs`, `fg` and `bg`, in one place (jobs.ts `jobOfSpec`): `%N`; `%+`, `%%` and a lone `%` for the current job; `%-` for the one before it (the current one when it is the only job); `%name` for the job whose command starts with name, and `%?text` for the one whose command contains text. `disown` and `jobs` take the word without its `%` too. A spec for no job is `%N: no such job` (127 for `wait`, 1 for the others), and a name or text that fits more than one job is `sl: ambiguous job spec`, which `disown` and `jobs` follow with `%sl: no such job`; `wait sleep` is `` `sleep': not a pid or valid job spec `` (1). `kill` returns 0 when its signal reached any of its targets, as bash's does. Different from bash 3.2: a name or text is looked for in the whole command as written, so for the job `sleep 1 | cat &` `%cat` names no job and `%?cat` names it, where bash 3.2 calls both ambiguous. `disown` is bash's: with no operand it takes the current job (the newest still running) off the list, `disown <jobspec>` and `disown <pid>` the jobs named, `-a` every job and `-r` every running one; `-h` leaves them listed and only spares them the shell's hangup. A disowned job's pid keeps status 0: `wait <pid>` answers 0 at once and the job runs on, as in bash. `fg` and `bg` say `no job control` in a shell without it (`sh -c`, a script, a subshell); jsh finds the job named, or the current one, says why when there is none (`fg: current: no such job`), and otherwise answers `not supported` (1). A name for no running job is `disown: %3: no such job` and no current job `disown: current: no such job` (status 1 either way).
  - A subshell, a background job and a pipeline stage start with no jobs, as bash's forked subshells do: their `wait` waits only for the jobs they start (never for the job they are, so a background `( … & wait )` ends), and `jobs`, `wait %N`, `wait $!` and `kill %N` there know none of the shell's jobs (`pid N is not a child of this shell`, `%1: no such job`, 127 and 1). `kill $!` still reaches the process. As in bash 3.2, a command substitution and a lone `jobs` run as a pipeline stage list the shell's jobs (`$(jobs)`, `jobs -p | xargs kill`, `$(kill %1)`); a substitution's `wait` does not wait for them. Still different: bash 3.2 answers `$(wait %1)` for a job still running with a silent status -1; webnode answers 127 with the 'not a child' message.
  - Without job control (a script, `sh -c`, a subshell or pipeline stage of jsh) a background command, group, subshell or and-or list reads /dev/null unless the command itself redirects its input, as in bash: any `<`, `<>`, here-document or here-string (whatever fd it names, so `cat 3< f &` keeps the shell's input too), or a copy or close of fd 0 (`<&0`, `0<&N`, `<&-`). Then its redirections apply to the shell's input as it was, so `seq 1 3 | { cat <&0 & wait; }` prints 1 2 3. Only the lone command's own redirections count: `cat <&0 && true &` and a function whose body redirects read /dev/null. The one exception, as in bash: a background pipeline of several commands (`a | b &`) keeps the shell's standard input. In jsh a job keeps the terminal, and a built-in in it that reads the terminal waits until the job is killed (bash stops the job with SIGTTIN).
  - A background command that cannot start is a job all the same, with a pid of its own from the 4194304 range: `$!` is set and `wait $!` gives 127 or 126. bash prints the `[1] <pid>` line before the error, webnode after it.
- jsh takes the terminal back after each foreground job (`tty.reclaim`). What the job leaves running (an orphan whose parent was killed), whichever program of a pipeline started it, moves together to the job's own process group, numbered by the first program jsh started for the job: a later Ctrl+C or key no longer reaches it, and `kill -- -<pid>` does. Until then the job runs in the shell's group. A pipeline's programs are all waited for before the prompt returns, even when Ctrl+C stopped its in-process stages.
- `jobs` and the notices at the prompt use bash's format (`[1]+  Running                 sleep 30 &`; `+` for the newest job, `-` for the one before; Done, Exit N, Terminated, Killed …), showing the command as written. An interactive shell also gives a job's notice when `wait` collects it (on `wait`'s standard error, so `wait %1 2>/dev/null` hides it), once a foreground program has ended, before the next command (on the shell's standard error), and before each prompt, also after an empty line or a Ctrl+C, as bash does. The words are Linux's strsignal (`Terminated`, `Interrupt`, `Killed`, `User defined signal 1`, `Broken pipe`); bash on macOS adds the number (`Terminated: 15`). A non-interactive `sh` gives no notice (bash prints `line 1: <pid> Terminated …` on stderr; dash nothing). Job numbers restart at the highest listed + 1. jsh announces a job it starts as `[1] <pid>` on stderr; a job a subshell or a pipeline stage starts is not announced, as in bash -i. `jobs` takes bash 3.2's options and job specs: `-l` puts the pid between the mark and the state (`[1]- 4194304 Running …`, five columns at least), `-p` prints only the pids (`jobs -p | xargs kill`), `-n` only the jobs that have ended or that `jobs` has not shown running yet, and with no operand `-r` only the running jobs and `-s` the stopped ones, of which there are none; of -l, -p and -n the last given wins, `-x` is not supported, and any other option is `jobs: -z: invalid option` with bash's usage line (2). A job that has ended leaves the list once `jobs` has shown its line; `-p` leaves it listed. Different from bash 3.2: a shell without job control keeps a job that has ended listed until `jobs` shows it or `wait` collects it, where bash drops it at its next command: `sleep 0.1 & sleep 0.3; jobs` prints `[1]+  Done …` and `sleep 0.1 & sleep 0.3; wait %1` gives 0, where bash prints nothing and says `%1: no such job` (127).
- A script the shell cannot read exits 126 (permission denied, or a directory); 127 only when it is not there. A command it may not run is reported in bash's words: `./dir: Is a directory` and `./file: Permission denied` (126), a name found on PATH by its PATH path (`bin/tool: Permission denied`, 126), and `command not found` (127) when PATH has no regular file of that name.
- **The terminal.** Input goes to the newest foreground process that is waiting to read the terminal: one that has it as stdin, or one that opened /dev/tty (a program that prompts inside a pipeline). As on Linux, a foreground process that never reads (a program under `tsx watch`) holds up none that does (the watch supervisor's Enter). A process that waits in a blocking call (spawnSync, execSync, a blocking read) reads nothing meanwhile: what is typed goes to the child it waits for, to its own blocking read, or to an older reader that is waiting, and otherwise stays in the terminal until the call returns. jsh and the shell's in-process readers read the terminal only while they need input. jsh gives the keys typed after a command line back to the terminal (`tty.unread`), so the command reads them, as in bash.
  - Keys typed ahead in raw mode, or given back, are edited and echoed when a cooked reader next reads them, as BSD's PENDIN does; a raw reader gets them as typed. A line still being typed when raw mode comes on (the start of the next command, typed while one runs) reaches the raw reader as typed, and an end of file typed ahead reaches it as Ctrl+D. Ctrl+C in cooked mode discards everything typed ahead and not yet read, as a terminal flushes its input queue on INTR. With two lines typed ahead in cooked mode, the second is echoed again when a cooked reader takes it.
  - What a process that reads the terminal as a stream was sent and never handed to its reader (it exited after one line, closed the terminal, or paused and never read again) goes back to the terminal when it ends, so a line typed ahead of the prompt is the shell's, as on Linux; a Ctrl+C discards it with the rest of the input.
  - A process that changed the terminal's mode leaves the terminal, when it ends (however it ends), in the mode it found, as Node (libuv) restores it: cooked after a program started from the prompt, still raw for a parent that had made the terminal raw. Turning raw mode off puts back the mode the process found when it turned it on, and asking for the mode it already has does nothing. A background job, or what an ended process left running, cannot change the mode.
  - When a process exits, what it started and left running (its orphans) loses the foreground: it keeps running in its group, so the terminal's Ctrl+C still reaches it until a shell with job control takes the terminal back, but it waits for input like a background reader and puts back the terminal mode it found. A process started beside the one that exits (a sibling) keeps the terminal.
  - A read of the terminal that returns no bytes while jsh edits a line is an end of file typed at the terminal: the Ctrl+D key. On an empty line jsh ends; with text on the line it reads on. Two in a row mean the terminal's input is over: jsh gives the line up and ends (bash 3.2 would run the half-typed line first).
  - A process can give up a read it waits in: `fs.readAsync(fd, length, position, signal)` (process/runtime.ts). When the signal aborts, a read still waiting for a pipe or a terminal ends with EINTR and takes nothing. The shell's built-in commands read this way.
- **A path reaches the filesystem as it is written.** A built-in command's operand, a redirection's target, the operand of `.`/`source` and the script the shell is started with are joined to the working directory and nothing more, as a node program's paths are. So `..` is resolved after the links before it (`cat link/../x` reads the file beside the link's target), every directory a path goes through must be searchable (`cat nx/../f` is refused), and a trailing slash asks for a directory (`rm link/` is `Is a directory`, `cp f nodir/` and `mv f nodir/` fail). An empty name names nothing: every command answers `No such file or directory` (`rm -f` ignores it) and none takes it for the working directory, so `rm -rf "$UNSET"` removes nothing. Only `cd` keeps bash's logical path: `cd link/..` comes back to where the link is, and `cd ""` stays.
- Pathname expansion lists a directory only for a component that holds a pattern, so it needs read on that directory; a component without one, and a trailing `/`, are tested with a stat and need only search on the way. With `nr` 0311 and `nx` 0644, `echo */in` prints `nr/in` and `echo n*/` prints `nr/ nx/`, as bash.
- **`umask`** is bash's: `umask`, `umask -S`, `umask -p`, an octal mask up to 0777 and symbolic modes (`u=rwx,g=rx,o=`, `g-w,o-rwx`, `+r`), with bash's messages (`sh: umask: 999: octal number out of range`; `` `z': invalid symbolic mode character `` for `umask u+z`; `` `q': invalid symbolic mode operator `` for `umask q=r`; status 1, and 2 with the usage line for a bad option). The main shell's mask is the process's, so the programs it starts inherit it. A subshell, a pipeline stage, a command substitution and a background job each keep a mask of their own, as bash's forks do, though they run in the shell's process: a subshell's mask is in force only for the length of each call that creates something and is passed to the programs it starts (process/programs/shell/umask.ts). Built-in commands create through their shell's filesystem (`CommandContext.fs`).
- **Permission errors are reported as GNU coreutils reports them**, and the command goes on with its other operands (exit 1). `rm -r` removes what it can and names each entry it may not remove (`rm: cannot remove 'd/a': Permission denied`), passing over the directories left non-empty above it; `-f` ignores only missing files. `ls` lists a directory it may read but not search, with `?` fields under `-l`, and ends its file operands with a blank line when directory operands follow, even ones it cannot open (`ls out nr` with `out` a file gives `out`, a blank line, then the error), as GNU ls. `ls -l` shows setuid and setgid as s/S over the user and group x, and the sticky bit as t/T over the other x (`ls -ld /tmp` gives `drwxrwxrwt`). `touch -c` passes over only a file that is not there; any other failure is `touch: setting times of 'X': <reason>` (exit 1), and a failed create without -c is `cannot touch`. `cd` prints bash's `cd: <dir>: Permission denied | Not a directory | No such file or directory`. `ln` names both ends of a hard link it could not make (`failed to create hard link 'link' => 'target'`). `grep -r` reports entries it may not look at. `sort` checks that every input is readable and opens its `-o` file before it reads; a failure is `sort: cannot read: F: …`, `sort: open failed: F: …` or `sort: read failed: F: …`, exit 2 with no output. A command whose standard input is closed (`cat <&-`) reports it as its GNU namesake does: the shell's read of standard input fails with EBADF in one place (io.ts `CommandIo`), and each command words it: `cat: -: Bad file descriptor`, `head: error reading 'standard input': …`, `wc` its row of zeros then `wc: 'standard input': …`, `cut: -: …`, `tail: cannot fstat 'standard input': …`, `tee: read error: …`, `uniq: error reading '-': …`, `tr: read error: …` (each 1), `sort: stat failed: -: …` and `grep: (standard input): …` (2); cat, head, wc, cut, tail and tee then say it once more, as GNU's do when they close standard input at their end (`cat: closing standard input: Bad file descriptor`, `head: -: Bad file descriptor`). `read` says `read: read error: 0: Bad file descriptor` (1), as bash. `/dev/stdin` with standard input closed names nothing (`cat: /dev/stdin: No such file or directory`), as on Linux. `sed` says `sed: can't read -: Bad file descriptor` (2), not measured against GNU sed; `xargs` and curl's `-d @-` take a closed standard input as empty.
  - `cp -r` goes on past what it cannot read. A directory it makes gets the source's mode less the mask, is made writable for its entries when its owner could not write it (the source's mode, or the mask's doing) and gets that mode back afterwards. `cp` leaves an existing destination its mode and gives a new file the source's permission bits less the umask (no setuid); `-p`/`-a` give a file or a directory, new or already there, its source's mode. `cp -f` removes a destination it cannot open and copies again. An operand that is a symbolic link is copied as a link with `-r`, `-P` or `-d` and through it otherwise. `cp -v` prints `'a' -> 'b'` before each file it copies (also when the copy then fails) and for each directory it makes, as GNU cp. `cp` copies a source that is no regular file (a terminal, a pipe, a device, the command's own `/dev/stdin` or `/dev/fd/N`) as it arrives, chunk by chunk, as cat reads it: `cp /dev/tty out` holds what was typed so far, Ctrl+D ends the copy and Ctrl+C ends it (130) keeping what came. `/dev/fd/N` for an fd that is not open is `cannot stat … No such file or directory`, as on Linux. Inside a tree, `cp -r` still reads such a file whole, where GNU cp -r makes a special file.
  - `cp` and `mv` name the target they computed (`ro/out` for `mv out ro/`, `./f` for `cp f .`, `rw/f` for `rw//`). A destination cp or mv may not look at is `cannot stat '<target>'` (what coreutils prints on Linux; GNU on macOS says `target 'dir/': Permission denied`). cp and mv know the same file, and a copy or move into itself, by the files' identity, not their spelling.
  - `mkdir -p` names the first directory it could neither make nor enter, with that directory's reason (`mkdir -p nx/a/b` with nx not searchable: `cannot create directory 'nx': Permission denied`; `mkdir -p file/x`: `'file': Not a directory`), and `-v` names every directory it made. `-m` sets the last directory's mode exactly. The directories `mkdir -p` makes on the way get a=rwx less the mask plus the owner's write and search, as GNU's do, so a mask like 277 does not stop it.
  - `sed -i` writes a new `sedXXXXXX` file in the same directory with the original's mode and renames it over the original, so it needs write on the directory, not on the file (`sed: couldn't open temporary file …`, exit 4, when it cannot); on a symbolic link it replaces the link with a regular file, as GNU sed does without `--follow-symlinks`; on what is not a regular file it stops with `couldn't edit X: not a regular file`, exit 4.
- History: a command typed on several lines is stored as one line (`for i in 1 2; do echo $i; done`) when that line means the same; otherwise it stays in this session's history only and is not written to ~/.jsh_history.
- The line editor measures characters by xterm's default (Unicode 6) widths, as the jsh terminal does. Emoji are 1 column there.
- The shell's `read` gives a program that reads the same pipe next what it took past its line, as bash leaves it there. It takes at most 4 KiB from a pipe at a time and gives back what it did not use (`fd.unread`) before a program starts, before `kill` sends a signal, when the shell ends (exit, or a signal it does not handle) and as soon as the shell stops to wait for anything else, so a child shell that is killed leaves the rest to its parent. A writer is ahead of a `read` loop by at most the pipe plus 4 KiB; bash reads a pipe a byte at a time, so its writer is ahead by the pipe alone. A shell killed from outside in the middle of a run of commands that never waits takes what it holds (at most 4 KiB) with it. `head -c N` reads only N bytes, and `head -n` reads 8 KiB at a time, as GNU head does: the rest is lost on a pipe, and on a file the shell opened it moves back. A file the shell opened for a compound command (`{ read x; node count.js; } < file`) is read at the shell's own offset, so the program gets the file from the start.
- **Built-in text filters stream.** grep, sed, tr, cut, uniq and xargs write as their input arrives and stop reading once their output is closed, so `dev-server | grep ready` prints at once. sort, wc and tail (on standard input) still read to the end first. Bytes that are not UTF-8 pass through every text command unchanged, and through `read` into a variable and out again; printf/echo `\NNN` and `\xHH` write single bytes.
- **`tail -f`** checks the named files every 250 ms. It ignores -f on standard input and ends on Ctrl+C (exit 130).
- **`rm -i` and `mv -i` cannot prompt**: without -f they refuse, printing "-i cannot ask for confirmation here" and exiting 1, instead of acting as if the user had answered yes. `rm` never asks: GNU rm at a terminal asks before removing a write-protected file (`rm: remove write-protected regular file 'f'?`); webnode removes it without asking, as GNU does when standard input is not a terminal. `rm` never removes an operand whose last component is `.` or `..`, nor `/`, however the root is spelled (`rm -rf //`, a link to `/` with a trailing slash: `it is dangerous to operate recursively on 'X' (same as '/')`). `rm -r link/` on a link to a directory empties the directory behind the link, as GNU rm on Linux does, and then prints `rm: cannot remove 'link/': Not a directory` (exit 1); `rm -rf link/` empties it and says nothing (exit 0). The directory itself stays (macOS rm removes it).
- **`xargs -P N`** is accepted, but the commands run one at a time. `-s` sets no limit.
- **`curl`**: the cookie jar (`-b`, `-c`) sees only cookies from local servers, because the browser's fetch hides Set-Cookie. For other hosts, `--connect-timeout` bounds the wait for the response headers. `--retry` retries on timeouts, on HTTP 408/429/500/502/503/504, and on a refused connection only with `--retry-connrefused`.
- **`sed`** still has no blocks, hold space, `N/D/P`, branches or `w`. An empty regex reuses the last regex in the script, not the last one run.
- **`grep -r`** skips symbolic links and binary files (a NUL byte in the first 8000 bytes), and prefixes names even for a single file operand, as BSD grep does. An operand `.` is part of each name (`./a.txt:…`), and names are bare only when -r has no file operand, as GNU grep.

The package manager:

- Registry requests time out when nothing arrives for 2 minutes (packuments and version documents) or 5 minutes (tarballs). The clock restarts with each chunk of the body. A request whose connection drops, even mid-body, is retried twice (after 300 ms, then 600 ms) before the install fails with EFETCH.
- `pre<script>` / `post<script>` hooks run for npm, pnpm, yarn and bun alike, as the real tools do (pnpm since v8).
- npm has the silent log level: `-s`, `--silent`, `--loglevel silent` (and `--loglevel=silent`), or `npm_config_loglevel` / `NPM_CONFIG_LOGLEVEL` set to silent. It prints no script header, no list of scripts (`npm run`), no install summary and no `npm error`/`npm warn` lines; `npm ls`, `--version` and `init`'s file are still printed. A level set on the command line (`-s`, `-q`, `-d`, `--verbose`, `--loglevel <level>`, the last one winning) reaches everything npm runs as `npm_config_loglevel`, as in npm 11.20. Not modelled: `--silent=true` and `--silent=false`, and npm's usage text for an unknown command at the silent level. No `.npmrc` is read (project, user or global): the log level comes only from the command line and `npm_config_loglevel` / `NPM_CONFIG_LOGLEVEL`, so `loglevel=silent` in a project's `.npmrc` still leaves `npm run` printing the script header, where npm 11.20 prints none.
- npm passes a failed script's exit status on without printing anything, as npm 10 and 11 do for `run`, `start`, `test` and `exec`; for a script that failed with an exit code, pnpm, yarn and bun print their failure lines. When what npm ran (a script, an `npm exec`/`npx` command, a bin) dies of a signal, npm dies of that signal, as @npmcli/run-script makes it; a signal a Node program survives (SIGPIPE, SIGUSR1) is reported instead (`npm error path … / npm error command failed / npm error signal SIGUSR1 / npm error command sh -c …`) and npm exits 1, at once where npm waits 500 ms.
- npm and pnpm pass SIGINT and SIGTERM on to what they run and die of any other signal; yarn passes on SIGTERM only, so Ctrl+C ends yarn itself. pnpm takes a script that SIGINT ended for one that ended well: Ctrl+C on `pnpm dev` prints nothing and exits 0 when the program died of the SIGINT, and a post script runs; when the program handled the SIGINT, pnpm gives the program's own exit code (130 under `tsx watch`) with its ELIFECYCLE line. Any other signal prints ` ELIFECYCLE  Command failed.` and pnpm dies of it (exit 1 for SIGPIPE and SIGUSR1); a failed `test` script is ` ELIFECYCLE  Test failed. See above for more details.`. yarn prints `error Command failed with signal "SIGTERM".` and exits 1.
- A failed install script of the project is reported as the tool reports it (npm: `npm error code 7 / npm error path … / npm error command failed / npm error command sh -c exit 7`; pnpm: its ELIFECYCLE line), and the install ends without its summary. The summary line (`up to date in …`, `added N packages in …`, `Done in …`) comes after the project's install scripts; pnpm's `Already up to date` comes before them.
- Still different: `pnpm exec`, `pnpm dlx` and a bin run by its name (pnpm, yarn) give 128+n silently when a signal ended the command, where pnpm prints ` ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL  Command was killed with SIGTERM (Termination): <cmd>` and exits 1 and yarn prints its `Command failed with signal` line. pnpm's failure lines go to standard error (pnpm writes them to standard output). pnpm's ` WARN   Local package.json exists, but node_modules missing…` and yarn's `info Visit https://yarnpkg.com/…` lines are not printed. npm, pnpm and yarn ignore SIGPIPE from their start, as Node programs do: a write to a pipe whose reader has gone fails, and nothing more is written there. When npm's own output has lost its reader (`npm run x | true`), npm ends at once with 1 and prints nothing; the script it has already started runs on to its end without it, and nothing after it (a post script) starts. npm 11.20 on macOS and npm 10.9.8 on Linux do the same. npm also prints `npm error A complete log of this run can be found in: …`, which webnode does not. A listing ends with its own status (`npm ls | true`: 0). pnpm survives the first write that loses its reader and dies of the next one: a lone script runs and pnpm exits with its status; with a pre script, the pre script runs and pnpm then exits 1 with Node's report of the unhandled EPIPE `error` event on stderr, before the script and its post script (pnpm 9.12.1). The report is Node 22.14's form without the stack frames that name pnpm's own source. yarn goes on and runs the script (0). The script header is one write, so `npm run x | head -1` gets all of it (0). A failed script's ELIFECYCLE line is that second write in real pnpm, which writes it to standard output: `pnpm run fail | true` dies of the EPIPE report there (exit 1), where webnode writes the line to standard error and exits with the script's status.
- A peer dependency is placed where it resolves to its dependent's own copy, so react-dom and the package that pins react share one React. A dependency cycle between different versions (a@1 → b@1 → a@2 → b@2 → a@1), which no node_modules tree can lay out, fails the install with "Cannot lay out a dependency cycle" instead of hanging.
- Overrides: plain `name → spec` entries in `overrides`, `pnpm.overrides` and `resolutions` apply everywhere, and so does an npm nested override's own `"."`. Overrides scoped to a parent or a version (`a>b`, `a/b`, `{ "a": { "b": … } }`, `"name@<2"`) are not applied; the installer warns about each one on every install.
